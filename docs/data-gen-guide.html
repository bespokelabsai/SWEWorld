SWEWorld · data_gen/

How data_gen builds a company

The pipeline that turns a real open-source repository into months of chat, wiki pages and mail for a company that never existed — with hidden requirements scattered through it, and every technical detail traceable to code that really was written.

What it is

data_gen/ generates the world's content. It reads the real curator repository — every commit, pull request and issue — invents a company that plausibly wrote it, and then simulates that company talking for months. The output is a corpus: chat messages, wiki pages, page comments and email.

real repo→grounding→company→day specs→planted clues→simulated talk→data/

Three parts of SWEWorld are easy to confuse. They meet at one directory:

data_gen/

Generates the content. Runs on your machine, costs real tokens, writes to data_gen/build/. That's this guide.

world/ + scripts/

Build and populate the container — Gitea, Mattermost, BookStack, mail. They ingest whatever is in data/.

task_generator/

Authors the tasks an agent is graded on, and plants their requirements into a corpus that already exists. See its own guide (local · published).

data/

The handoff. install_corpus.py writes a finished run here; make bake-image ingests it into the image.

The governing rule is that nothing technical is invented. People, project names and conversations are fiction, but the files, symbols, commits and dates they discuss are taken from the real repository. That is what makes a planted requirement checkable later.

The two chains

This is the thing to get straight first: there are two separate numbering schemes, and they are unrelated. Stages 0–2 read the real repository and answer “what is true”. Phases 1–4 build the synthetic company on top of that. Stage 1 is build_episodes.py; phase 1 is phase1_company_grounding.py. They have nothing to do with each other.

Every step reads its predecessor's JSON out of data_gen/build/, so the pipeline is a chain of files on disk rather than one long process. You can stop, inspect, and pick up again.

Glossary

grounding
What was measured about the real repo (subsystems, tests, contributors, hotspots), plus an optional model-written interpretation of it. Measured and interpreted keys are declared separately in the file.
episode
One unit of real work: issue → branch → commits → pull request → review → merge, collapsed into a single record.
workstream
A multi-week thread of work that people would name, clustered from episodes.
artifact
A document or mail the calendar says someone will write, fixed before any day is generated, so no day cites a page nobody wrote.
day spec
One conversation plan, per channel per day: who speaks, about what, and what should be settled by the end.
fact
One of a requirement's five atomic parts: rule, scope, exclusions_or_crossover, failure_behavior, observability. A fact no remark carries makes the task unscoreable.
leaf / clue
One remark, at most two sentences and 30 words, carrying at most two facts. More than that and it reads as a specification rather than a thing somebody said.
herring
A decision the team really made and later reversed, planted strictly before the remark that overturns it.
carrier / slot
Where a clue can land: an existing conversation spec, a wiki page, a page comment, a mail message, or a forge issue.
run
One phase-4 simulation, under build/phase4/runs/<name>/, with latest pointing at the newest.

Stages 0–2: read the real repository

Deterministic wherever possible. The point is that no later step has to invent a file, a symbol or a date. Run from the repo root.

  1. extract_repository_history.py

    no modelstage 0
    python3 data_gen/extract_repository_history.py -v

    Mines the repository once: every commit on every ref, plus pull request, issue and review state from the GitHub API. It keeps the actual code — the blob before, the patch, the blob after.

    Writes
    build/repository_history.json and build/repository_blobs/, content-addressed by git blob SHA.
    Needs
    A GitHub token only when it refreshes: --token, $GITHUB_TOKEN, $GH_TOKEN or .env. --no-github and --no-refresh skip that.
    Flags
    --repo --rev --since --until --out --blobs-dir --cache-dir --token --no-refresh --no-github --no-patches --no-blobs
    Note
    Lockfiles, cassettes and binaries are skipped by a noise pattern, and skips are reported rather than silent. --no-patches drops the structural record to roughly a sixth of the size.

  2. build_episodes.py

    no modelstage 1
    python3 data_gen/build_episodes.py -v

    Collapses issue → branch → commits → pull request → review → merge into one episode each, with the pull request as the anchor. Commits with no pull request are grouped by author, time and paths.

    Writes
    build/engineering_episodes.json
    Needs
    No token, normally. It reads the stage-0 record (--history, which defaults to build/repository_history.json). It only calls GitHub when that file is missing or you pass --from-api.
    Note
    Gaps are recorded, never filled: a squash-merged pull request reports one commit in the clone beside six on the branch, and says so in provenance_gaps. --no-github costs every episode its review provenance.

  3. analyze_repository.py

    ~$3, ~13 min coldstage 2
    data_gen/.venv/bin/python data_gen/analyze_repository.py -v

    Measures the codebase's shape — subsystems, interfaces, tests, config, CI, dependencies, hotspots, contributors and ownership — then has a model interpret that evidence into eras, people, process and capability areas.

    Writes
    build/engineering_grounding.json. Which keys were measured and which interpreted is declared in the file itself.
    Needs
    The anthropic SDK, hence the venv, and ANTHROPIC_API_KEY. --no-enrich runs measured-only on the system interpreter.
    Read
    It hard-fails when layout discovery isn't confident, rather than writing an empty analysis and exiting 0 — which is what it used to do. Citations are verified, but problems are flagged in the output rather than failing the run.

  4. make_report.py

    no model
    python3 data_gen/make_report.py

    Projects the grounding and episodes into build/report.html, one browsable page. It computes nothing new; it exists so you can check the record by eye before spending anything on phases.

repolib.py, and why re-running is cheap

Every script imports repolib as rl. It holds the path constants (build/, cache/, curator/), a read-only Git handle, the logging helpers (rl.ok, warn, info, and fail, which exits rather than raising), and rl.LLM, the model client.

Every answer is cached

Keyed by a hash of model, effort, system prompt, prompt and schema — plus, on the CLI backend, the model that actually answers (answered_by: cli:<cli_model>), after an Opus --audit-only replayed Sonnet's verdicts as its own. Old keys are still read, but an entry recorded from a different model is skipped. One JSON file per call under data_gen/cache/llm/; re-running a step that hasn't changed costs nothing.

--no-refresh never opens a socket

A cache miss raises, naming the step. That makes it the safe way to rebuild something from what you already paid for.

Credentials come from .env

env_value checks the environment, then data_gen/.env, then the repo root .env. That's how GITHUB_TOKEN, ANTHROPIC_API_KEY, CLAUDE_CODE_OAUTH_TOKEN, WORLD_DOMAIN and MM_TEAM_NAME are all found.

Cost is counted honestly

Cache-creation and cache-read tokens are billed at their own rates. Counting input tokens alone understates a run by an order of magnitude.

Phases 1 and 2: build the company

  1. Phase 1 — phase1_company_grounding.py

    model
    python3 data_gen/phase1_company_grounding.py

    Turns the grounding into a company: a name, a roster, who owns which service, how each person writes, and the chat channels. Nobody is invented — each employee is one real contributor under a new name.

    Writes
    build/company_grounding.json, plus two projections into the world: data/identities.yaml and data/channels.yaml.
    Gate
    A leak scan. Every real identifier must stay inside the real and identity_map blocks; one hit anywhere else fails the run and nothing is written. It also fails if a forge login can't be mapped to the roster.
    Careful
    It refuses to overwrite a hand-edited data/identities.yaml or data/channels.yaml — it asks git whether the file still matches HEAD. Use --force, or --no-emit-world-data to leave data/ alone.
    Note
    It needs a grounding with a people section, so stage 2 must have run with enrichment. There is no --backend or --auth here.

  2. Phase 2a — phase2_timeline.py

    no model, no network
    python3 data_gen/phase2_timeline.py

    Pure arithmetic over the mined record: for each day, what was committed, which pull requests were open, what shipped, who was present, and which files and symbols existed. This is the substrate every interpreting phase reads.

    Writes
    build/timeline.json. Same bytes every run.
    Note
    Days are the author's local day, not UTC. Bucketing by UTC invented 302 weekend commits against a real 252.
    Note
    A missing data/history/manifest.json is a warning, but then nothing a spec cites can be opened in Gitea. Run make history first if you want that link to work.

  3. Phase 2b — phase2_workstreams.py

    model (names and titles only)
    python3 data_gen/phase2_workstreams.py

    Clusters episodes into workstreams people would actually name, and fixes a calendar of documents and mail before any day is written — which is what keeps days independent and stops a day citing a document nobody has written.

    Writes
    build/workstreams.json and build/artifacts.json
    Gate
    Every episode in exactly one workstream, every author present on the day. It runs before the model stage, and nothing is written if it fails.
    Note
    The clustering and the calendar are deterministic; the model only writes names and titles, so --no-enrich gives you the structure for free.

  4. Phase 2c — phase2_days.py

    one call per day
    python3 data_gen/phase2_days.py --only 2025-03-11 2025-03-12   # or --from / --until / --limit

    For each conversation-worthy day, writes a deterministic state file (what the project knew that morning) and, with one model call per day, the conversation specs — one per channel that had something to say.

    Writes
    build/days/state/YYYY-MM-DD.json and build/days/specs/YYYY-MM-DD.json
    Note
    State files are written unconditionally, before any early return. A day's spec only lands if it passed verification, so “all N days verified” is a real guarantee rather than a problem count.
    Careful
    --attach-only binds artifacts to existing specs with no model call, but it overwrites phase 2b's artifacts.json with resolved authors.
    Note
    Conversations are weekday-only — weekend work surfaces on Monday — and need at least two speakers.

Phases 1, 2b and 2c take --no-refresh (cache only) and --no-enrich (skip the model). Phase 2a takes neither, because it makes no model calls at all. Only 2b, 2c and phase 3 take --backend and --auth.

Phase 3: hiding the requirements

The conceptual core. A task states a feature openly and hides requirements written down nowhere. Each hidden requirement is decomposed into a tree — subconclusions a reader has to infer, and leaves, individual remarks that imply them — then scattered across months, channels and sources, so that no single sitting recovers it.

python3 data_gen/phase3_plant.py --pick t1,t12,t23 --backend sdk --auth api-key

Phase 3 is entirely one-shot calls, so run it on the API key. The CLI backend cold-starts a session per call, about 25 seconds each. --limit defaults to 5, and takes the first five tasks in the file — which is not a sample of anything, so use --pick when you mean specific tasks. input/tasks.json holds 60 hand-written tasks, each with 2 hidden requirements.

Nothing is written until the tree is proved solvable

Every gate below fails the whole run, and the failure feeds a bounded re-plant that is told what the last attempt got wrong.

GateCostsWhat it catches
every fact carriedfreeA fact no leaf covers. The corpus could never teach it, so the task can't be scored.
giveaways()freeA leaf that restates the requirement's own wording, or types a term it was forbidden to type.
spread_problems()freeToo concentrated: fewer than 2 sources, 3 weeks or 2 rooms — or two leaves of one subconclusion in the same room within a fortnight.
solvabilitymodelReconstruct then grade, as two separate calls, best of three. One model rebuilds the requirement from the remarks with no answer key; a second grades that reconstruction. A grader that has seen the answer agrees with itself, which is why it is two calls.
…with the herrings inmodelThe same proof run again with the reversed decisions present. A fact recoverable clean but lost in the noise is reported as drowned, separately from one that was never there.
not_fragmented()modelA subconclusion one remark settles on its own — which makes every other remark under it decoration.
tree_adds_up()modelSubconclusions that don't reach the requirement: a reader could get all of them and still not have it.

What it writes, and what it overwrites

Writes
build/clues.json (the ledger, written first on purpose), build/phase3_plant.md (the human report), and build/phase3_forge.json when any clue landed on a forge item.
Dry run
--dry-run still makes every model call and still overwrites clues.json and phase3_plant.md. It skips only the corpus: the specs, artifacts.json and phase3_forge.json.
Rewrites
Every file in build/days/specs/, not only the days it touched, plus build/artifacts.json. Back both up before a re-plant.
Why
It re-plants cleanly because strip_previous() removes the last plant first. Without it, the stage reads its own output and adds to it — the same clue in four rooms, which breaks the one-clue-per-carrier rule the design rests on.
Sources
--sources defaults to slack,notion,email. github becomes available only when build/forge_plan.json exists, written by scripts/ingest_forge.py --export --plan-out, because a clue in a pull request that nothing posts is a clue that never lands.

Phase 4: the specs become conversations

Phase 4 hands each day's specs to persona agents and lets them talk. The engine is bespoke_user, installed separately at ~/.local/lib/python3.10/site-packages/bespoke_user/ — not in this repo. phase4_simulate.py owns all the domain knowledge; phase4_run.py is the engine half, imported only after authentication is settled.

python3 data_gen/phase4_simulate.py --day-count 3 --dry-run   # free: writes the review doc and stops
python3 data_gen/phase4_simulate.py --day-count 3 --run march-slice

People get the company's apps as tools

worldapps.py gives each persona MCP tools that write the ingest schemas directly, so a page written in conversation lands as the exact Markdown and frontmatter the ingest will parse. A private format plus a translation step would be a second place for the schema to be wrong.

ToolCanWrites
Wikiwrite, read, list, commentdocs/<collection>/<page>.md with title/author/created_at frontmatter
Mailsend, reply, check inbox, reademails/ as real .eml with proper threading, plus an index
Forgefind and read issuesnothing — read-only, so a persona cites a real pull request instead of inventing one
Reporead, list, search, recent commitsnothing — and it is bounded by the clock, so a file added in July does not exist in March

Every planted clue is checked against what was actually said

A persona's words are their own, so a clue doesn't have to be worded as planted — but the information has to be there, and any identifier has to appear literally. Four rules, each of which was a real failure first:

  • The whole remark is judged, element by element, not against the one-line clause that summarises it. Free phrasing is not free abridgement: what a persona reliably keeps is the flat observation, and what they drop is the half that says why anybody minds — which is the half that tells a reader there is a requirement here.
  • Identifiers are matched in code, normalised for backticks and casing, so a judge never decides whether a name was typed.
  • Information, not speech act. A point made inside a question still counts; the old gate threw away a clue whose fact was stated perfectly, inside a question.
  • A miss returns a list of what was missing, not a boolean. A retry that can't say what was missing is the same attempt again.

Two failures, two costs

Nobody said it

The channel-day runs again, told what was missing. Up to --clue-tries times.

Said, but thinner than planted

Repaired where it stands (--clue-repairs): the holder sends the missing part as one more message, seconds after their own. Re-simulating a whole day for half a remark re-rolls every other clue in the room that was already right. Repairs are named in clues/<id>.md under Repaired, never silent.

The run directory

build/phase4/cast.json          # SHARED, one level up — never per-run
build/phase4/latest -> runs/<run>
build/phase4/runs/<run>/
  context.md                    # everything a model will be told
  transcript.json               # the merged conversation
  messages.jsonl                # the chat projection the ingest reads
  docs/ · emails/ · comments.jsonl
  clues.json + clues/index.md + clues/<id>.md
  activity.json                 # every tool read a persona made
  artifacts.json + artifact_audit.md
  run.json · cast.json (a copy, so the run is self-describing)

cast.json sits at the phase-4 root because it holds each persona's voice. Redrawing it per run would give the corpus a person who writes one way in February and another in April. Everything else is per-run because the stores are append-only: a three-day February run once inherited two “week of Mar 31” mails from the run before it.

Two gates run before a token is spent: a planned artifact kind that nothing will consume stops the run, and clue problems — an empty or question-shaped settle clause, a required identifier missing from the day's allow-list — are named up front, because finding them later costs a paid re-run per channel-day.

When a conversation comes out wrong, read <run>/context.md. It is exactly what the model was told, so the fault is diagnosable there rather than by re-running.

The auth trap, worth knowing before you run anything

Persona turns and one-shot calls authenticate differently, and both fail silently the wrong way round.

Persona agent turns

Run on CLAUDE_CODE_OAUTH_TOKEN, the subscription. They are almost all the tokens.

One-shot calls

The director, the landing judge, the clue judge and all of phase 3 run on ANTHROPIC_API_KEY. Routing a one-line question through the agent path cold-starts a session every time, which is how an 18-turn conversation becomes half an hour.

phase4_simulate.resolve_auth() settles this before any import that reaches the engine, because the engine decides once, the moment it is first touched. Nothing afterwards may re-read ANTHROPIC_API_KEY — it has been removed from the environment on purpose. That is the whole reason phase4_run.py is a separate module imported inside a function.

From a run to a populated world

python3 data_gen/install_corpus.py --run <run> --dry-run
python3 data_gen/install_corpus.py --run <run>
make bake-image TAG=<next>

install_corpus.py is the supported handoff, and it validates rather than just copying. It replaces what it owns — docs/, emails/, messages.jsonl and comments.jsonl — deleting each first, because a merge leaves the previous corpus sitting beside the new one, indistinguishable, and the ingest would import both.

It never touches

identities.yaml and channels.yaml (phase 1 writes those), commits.jsonl and history/ (they come from make history on the host), and schemas/, which is hand-written contract, not output.

It checks before declaring success

Collections match directories both ways, page frontmatter holds exactly the allowed keys, every .eml is indexed and every indexed path exists, and chat rows carry channel, author and timestamp. Any problem fails, and nothing is reverted.

It also drops the duplicates listed in data_gen/input/superseded.json: runs made before the simulator learned to clear a day hold the same page and mail once per pass over that day.

The gate before a bake: scripts/check_corpus.py

Syncing the tool clock to the turn clock cannot make a persona write a page before announcing it, and the ingest validates each file alone. So make bake-image runs check_corpus.py first (and --plants; CORPUS_CHECK=0 skips both) — sweworld:0.4.9 shipped 175 contradictions without it. It reads files against each other: a page announced before it exists, a comment older than its page, a mail reply dated before the mail it answers, a PR discussed before it was opened. --fix retimes pages and announcement mails to agree with the chat, never past a comment or a reply. Artifacts may be retimed; chat may only be reworded, because planted clues anchor to "HH:MM author".

Cost, and how not to spend it

A full phase-4 corpus run is tens of hours. A three-day slice is about twenty minutes. Stage 2 is roughly $3 and 13 minutes cold. Everything else is expensive to regenerate, so know what a step overwrites before you start it.

  • --dry-run on phase 4 writes <run>/context.md and spends nothing.It still creates the run directory and repoints latest. The earlier phases have no dry run.
  • --dry-run on phase 3 is neither free nor read-only. It makes every decompose and prove call, and overwrites build/clues.json and build/phase3_plant.md; only the specs, artifacts.json and phase3_forge.json are spared.The ledger is written before the flag is read, so a formatting error can't throw away an hour of generation.
  • --no-enrich gives you the deterministic half of a phase with no model calls at all.Available on stage 2 and phases 1, 2b and 2c.
  • --no-refresh rebuilds from the cache and refuses to open a socket.Not on phase 2a, which has nothing to cache.
  • Slice the days. --only, --from, --until and --limit on phase 2c; --days and --day-count on phase 4.Regenerating every day blindly is the expensive mistake.
  • Back up before any phase-3 run, dry runs included. Copy build/clues.json and build/days/specs/ first.Phase 3 rewrites every spec file, not just the ones it touches, and even a dry run replaces the ledger.

Pitfalls

The two numbering schemes are unrelated.

Stage 1 is build_episodes.py. Phase 1 is phase1_company_grounding.py. Nothing connects them but the word.

build_episodes.py does not need a GitHub token.

It reads the stage-0 record by default. Only --from-api, or a missing record, sends it to the network.

Phase 1 writes into data/.

It projects identities.yaml and channels.yaml directly. Pass --no-emit-world-data if you don't want that.

Phase 3 rewrites every day spec.

Including days it never touched. Back up first; strip_previous() makes the re-plant clean, not reversible.

Auth is decided once, on first touch.

Which is why the engine is imported behind a function call, and why nothing may read the API key afterwards.

A corpus reaches the world only through install_corpus.py.

Phase 4's own --install copies the same four things but skips every validation and the superseded-duplicate cleanup.

Today's corpus in data/: 9,802 chat messages, 108 wiki pages and 93 mails (613 .eml files, one per mailbox copy). It began as an install of the corpus run but is no longer a copy of it (that run now holds 9,592 messages, 114 pages and 679 mail rows): data/ has since been pruned by superseded.json, hand-reworked where tasks plant into it, and retimed by check_corpus.py --fix. Re-installing would undo all of that.
