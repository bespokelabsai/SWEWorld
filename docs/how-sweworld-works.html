01 — The idea

A requirement nobody wrote down

Give an agent a ticket that says add an output cap to the code executor and it will write something reasonable. Whether it writes the right thing depends on facts that live in no specification: that the cap is counted per stream and not per process, that exceeding it truncates from the middle rather than the tail, that the sentinel a truncated stream carries is spelled …[capped]… and is checked elsewhere by an exact match.

In a real company those facts exist. They are just not in the ticket. They are in the thread where two people argued about it in February, in a wiki page somebody updated afterwards, in a comment on that page, and in a mail thread that reversed an earlier decision. An engineer joining the team recovers them by reading, asking, and noticing that the January decision was overturned in May.

SWEWorld builds that company so the recovery can be measured. One container runs a real Gitea, a real Mattermost, a real BookStack wiki and a real mail server, populated with fifteen months of chat, documents and mail generated for it. The product the company ships is real too: bespokelabs/curator, vendored and served from the in-world git server with its history rewritten onto the company's own people.

The agent works inside as an ordinary engineer: no sudo, and code reaches a running service only by being pushed and passing CI. What is measured is not whether it can code. It is whether it can find out what it was supposed to build.

02 — Orientation

Three machines that share one repository

Almost every confusion about this repo comes from mistaking one of these for another. They run at different times, on different hardware, and cost different amounts of money.

data_gen/ generates the content. It runs on your machine, spends LLM tokens, and writes to data_gen/build/. A full phase-4 corpus run is tens of hours; a three-day slice is about twenty minutes.

world/ and scripts/ build and populate the container. data/ is the handoff between the two halves: everything under it except data/schemas/ is generated.

task_generator/ and harbor_tasks/ make and measure the tasks. The first authors a task and emits it; the second is where the emitted arms and the graders that score them live.

make run gives you an empty world.

That is the base image by design, and it is the single most likely thing to confuse someone who opens BookStack and finds nothing. Populate with make bake-image, or ingest into a running container — order matters there, because comments need their pages to exist first.

Boot order

Build-time seeding runs in numbered dependency order: users and directories, then the datastores, then mail, then Gitea (which pulls in the curator import), then BookStack, then Mattermost. How code reaches a running service

This is the part that makes the world a workplace rather than a file tree. The agent cannot restart anything; it can only push.

The Makefile

make build-image      sweworld:dev — services, no content
make run              boot and publish every service
make verify           33 acceptance checks against the running world
make shell            a shell in as the agent (ubuntu, no sudo)
make history          HOST ONLY: rewrite curator/ history into data/history/
make bake-image TAG=… boot base, ingest data/, gate on verify, commit
make push-image TAG=… deliberately separate from bake

There is no test suite. world/bin/world-verify is the acceptance gate, and it checks the running world rather than the code: every supervised service, every vhost, the service APIs, IMAP and SMTP, the admin login on all four apps, the curator repository and its history, the privilege model — and the corpus minimums, so a bake cannot quietly publish an empty world. make bake-image refuses to commit unless it passes.

make history is the only target that touches curator/, read-only, and the only one that runs outside a container.

04 — data_gen

Where fifteen months of company history comes from

Two chains run here. The first reads the real repository and invents nothing technical; the second builds the world's content on top of it.

Stages 0–2 — read the real thing

Deterministic wherever possible. extract_repository_history.py mines every commit, PR, issue and review with before/after blobs; build_episodes.py turns that into PR-anchored engineering episodes; analyze_repository.py works out the repository's shape — subsystems, interfaces, CI, ownership; make_report.py renders both groundings as a readable HTML report.

Phases 1–4 — build the content

Each phase reads the previous phase's JSON. Run them in order.

PhaseScriptAnswers
1phase1_company_grounding.pywho works here, who owns what
2aphase2_timeline.pyproject state per day — pure arithmetic, no model
2bphase2_workstreams.pythreads of work, and the docs and mail they produce
2cphase2_days.pyone conversation spec per channel per day
3phase3_plant.pyhide requirements as scattered clues
4phase4_simulate.pythe specs become actual messages

The result, as installed today: 9,802 messages across 161 days (October 2024 to January 2026) in ten channels, 108 wiki pages in six collections, 613 emails across 23 mailboxes, 17 page comments, and 24 personas at world.local.

repolib.py is the shared infrastructure: a disk-cached Claude client, path constants, git access, logging. Every LLM response is cached by model, effort, prompts and schema, so re-running costs nothing and --no-refresh never opens a socket.

Phase 4 — simulation, and what it checks

Phase 4 drives a persona engine whose tools write the ingest schemas directly: a page written in conversation lands as docs/<collection>/<page>.md with the frontmatter the ingest script parses. Personas' voices live in cast.json at the phase-4 root rather than per run, because redrawing them per run would make one person sound like two across the corpus.

Then every planted clue is checked against what was actually said. A clue need not be worded as planted — the persona's words are their own — but the information must be there, and any identifier must appear literally. The check runs element by element over the whole planted remark, never against the one-clause summary of it, because what a persona reliably keeps is the flat observation and what they drop is the half that says why anybody minds — which is the half that tells a reader there is a requirement here at all.

Two failures, two costs. A clue nobody said re-runs the channel-day. A clue said thinner than planted is repaired where it stands: the same person sends the missing part as one more message seconds later. Re-simulating a whole day for one half-said remark re-rolls every other clue in the room that was already right.

05 — The conceptual core

How a requirement gets hidden

A task states its feature openly and hides requirements written down nowhere. Each hidden requirement is decomposed into a tree — subconclusions a reader must infer, and leaves, individual remarks that imply them — and the leaves are scattered across months, channels and sources so that no single sitting recovers the whole thing.

The vocabulary, which recurs everywhere downstream

  • fact — a requirement's five atomic parts: rule, scope, exclusions_or_crossover, failure_behavior, observability. A fact nothing carries makes the task unscoreable.
  • leaf / clue — one remark. covers names which facts it carries, settles is the third-person clause phase 4 turns into an end state, and verbatim names identifiers that must appear literally.
  • herring — a decision the team really made and later reversed.
  • carrier / slot — where a clue lands: an existing conversation, a wiki page, a page comment, or a mail message.

The gates, all of which fail the run

Every fact carried; no leaf restating the requirement's own wording; the spread requirement above; solvability proved by a closed-book reconstruct-then-grade, voted best of three, with the herrings present; and a structural check that no single remark closes its subconclusion alone while the subconclusions together still reach the requirement.

A name cannot be inferred; a value usually can. If no remark ever types plan_fingerprint, the attribute the test reads does not exist and the fact scores zero however well the corpus is read. Nobody needs a remark printing a hash, as long as somebody says which string was hashed and how much of the digest was kept. So the emitters refuse an arm whose remarks never type a graded name, and merely report the values.

06 — task_generator

Authoring a task, and proving it discriminates

The first sixty tasks were written ticket-first, with hidden requirements attached afterwards. Measurement said what that cost: a large share of their facts were coincidences, passed by an implementation that had never seen the requirement — and each was discovered only after a paid agent trial.

So task_generator inverts it. It designs the whole implementation first and cuts it afterwards, then proves the cut discriminates before spending anything on an agent.

author → build oracle → split → tests → build naive/spec → bracket → emit
      → clues → settle → reverse → reorder → reknit → prove → horizon → trial

The bracket is the gate

One suite, four independently built trees, a verdict per fact. It is free and takes about a minute, against roughly nine dollars for the agent trial it replaces.

VerdictpristinenaiveoracleWhat to do
hiddenfailfailpassship it
coincidencefailpasspassextend the specification — do not re-cut
vacuouspasspasspassthe test does not require the feature to exist; fix the test
broken——faila real defect. Stop here
unreachablefailfailpass, spec failsthe requirement does not say what the suite grades

A coincidence is a fact about the specification, not about the cut. When the bracket reports one, the instinct is to hide different facts. That does not work: re-cutting only chooses which parts to hide, and if every part was derivable from the surrounding source, each new cut is as bad as the last. What works is extending the specification with parts carrying content the codebase cannot supply — an invented name, a chosen value, a policy with no local evidence, or a deliberate departure from what the surrounding code plainly does.

The test that decides whether a part is really hidden

Could a competent engineer, with the ticket and the surrounding source, arrive at this by reading? If yes it is not hidden, however many alternatives exist. This is stricter than "name two plausible alternatives", and it is the rule the whole authoring prompt now turns on.

What is automated, and what is not

Every stage is automated: the specification, the oracle patch, the cut, the suite, the naive build, the bracket, the emitted arms. The judgement between stages is not. Two things are irreducibly human — choosing an area where two sides genuinely disagree and the disagreement is reachable, and writing the brief that names exact files and line numbers. A brief pointing at an area with one obvious implementation produces facts the bracket will reject.

07 — The measurement design

The arm ladder

A low blind score on its own is ambiguous between three different failures: the agent could not build the feature, could not find the evidence, or found it and could not use it. Each arm removes one of those explanations, and the whole design is the difference between them.

blind
the ticket alone.Should score ~0. If it scores 0 and the open feature passes, the agent built competently and recovered nothing — which is the load-bearing part of the zero.
spec
the ticket plus the hidden requirements, stated outright.Should score ~1.00. This is the proof that the suite is satisfiable and the requirements as written are sufficient.
clues
the ticket plus every planted remark, quoted inline in date order, herrings included and unlabelled.The ceiling: can an agent use scattered evidence once it has already been pulled out for it?
world
the blind ticket, byte for byte, against a populated image whose chat, wiki and mail genuinely contain those remarks.The real article: can it find the evidence itself?
world-located
the world arm with the search already done — the agent is told which pages and days hold the evidence.Splits retrieval from reading: handed the right rooms, does it still miss it?
…-hosted
the same arms built FROM the published registry image, pinned by digest.Horizon cannot resolve a local tag, so the hosted twins differ only in their base.

Reading them against each other is the whole method. clues matching its spec twin means the plant is sufficient and any blind gap is retrieval. clues matching the blind arm means the plant is too thin and no amount of corpus work will fix it.

Only world* arms boot the populated image; every other arm must see an empty Mattermost, or the corpus stops being the one variable between them.

A name being present is not the same as a decision being made. A clues arm can have every graded identifier typed somewhere, by any regex you like, and still be met by runs that build the ticket and ignore the remarks. The check that catches this decomposes each requirement against its own test assertions — atomic by construction, and what is actually scored — and judges each one stated / implied / absent / not_required against the corpus. implied is the finding: true, in the right room, in the right voice, and it tells nobody to do anything.

08 — harbor_tasks/_suites

Grading, and the forgery that shaped it

Grading runs inside the container against what the agent pushed — not its working tree, and not the deployed release. That separation is what makes a result readable: the provenance checks say separately whether the change was pushed, whether CI went green and whether it deployed, so an agent that wrote the right code and never deployed it scores zero on provenance and full marks on the requirements, instead of one shared zero that could mean either.

Importing the submission is executing it. When the grading pytest ran as root with the submission early on the path, a pushed sitecustomize.py ran as uid 0 before a single assertion, rewrote the grader's own score.py, and returned every subscore at 1.0 from a tree that implemented nothing. Dropping to an unprivileged uid removed that — and did not remove score forgery, because the same child still wrote the report the score was read from: an atexit hook in the submission rewrote junit.xml and produced reward 1.0 from a pristine tree.

A uid cannot fix that. The fix is structural.

score.py folds outcomes into per-fact reward keys — g1.r1.rule and friends — seeding every expected key at 0.0 first, so a suite that could not even run scores zero rather than silently omitting keys. The headline reward is the mean over hidden facts and excludes the open feature, which is why the open feature is reported separately: a blind arm scoring 0.00 with the open feature at 1.0 means something completely different from one scoring 0.00 with the open feature at 0.

The same score.py is imported by the local bracket rather than reimplemented, so a fact key means exactly the same thing in a free local run and in a paid hosted one.

09 — Running the experiment

Measuring

Locally first — one machine, one model, the instruction the only variable — and spend hosted rollouts only on what the local bracket cannot answer. A hosted average multiplies a completion rate by a recovery rate, and five rollouts cannot separate them.

Two numbers are the verdict

spec ≈ 1.00 says the suite is satisfiable. blind ≈ 0.00 says the requirements are genuinely hidden. Everything else is diagnosis.

When several facts fail together

Perfectly correlated per-fact failures are one defect, not variance. Three facts failing together on the same runs with byte-identical assertion errors is a single ambiguous sentence somewhere, not three problems. Find it before sampling more, and read the failing assertion's two sides rather than the fact's name.

Hosted runs

The hosted platform's CLI lives in its own virtualenv outside this repo. Pushing writes a binding file recording the task's server id and version — losing it makes the next push create a second task rather than a new version, which is why those files are deliberately not gitignored. Validation in the hosted idiom is this repo's own bracket: an oracle agent must come back 1.00 and a noop agent 0.00.

The agent type is a function of the task format.

The apex-format arms and the harbor-format arms have different rosters. Submitting a harbor task with the apex agent type fails the whole evaluation in about three minutes with zero rollouts, zero spend, and a step trace that looks exactly like an exhausted budget. Check the format in the binding file before you start debugging credentials.

While an evaluation is running, its status table lies.

The rendered table shows every unfinished rollout as failed with no score — indistinguishable from twenty genuine failures. The truth is in the JSON: one field counts what actually errored, another counts what has finished. An evaluation was once cancelled on the strength of that column while all twenty runs were healthy and mid-flight: seventeen dollars spent, no refund, no measurement.

Rollouts are pulled back as per-run JSON carrying the score and a subscore map keyed exactly like the local bracket, so a hosted number and a local number are directly comparable. Reading them is its own discipline: cross-check each transcript against the answer key remark by remark, because the subscores only tell you where to look.

11 — Hard-won

Things that cost real debugging time

The auth split

Persona agent turns run on the CLI subscription token; one-shot calls — directors, judges, and all of phase 3 — run on the API key. Both fail silently the wrong way round. The decision is made once, the moment the persona package is first touched, which is why auth resolution has to happen before any import that reaches it. Phase 3 is entirely one-shots, so run it on the API key: the CLI backend cold-starts a session per call, about 25 seconds, against seconds for the API path.

Which name each service wants at the login box

Gitea and Mattermost want the username (worldadmin). BookStack and Roundcube want the email (worldadmin@world.local).

Backdating BookStack means four tables, not one

entities, comments, page_revisions and activities. Correcting only the first two leaves a wiki whose pages read right but whose Recent Activity feed — the dashboard's main content — says "World Admin created page X, 3 minutes ago" for the entire world.

maddy creds create exits 0 when it fails

It once shipped a mail server with zero accounts while logging 15-mail: OK. The bootstrap script now asserts the account exists afterwards.

Offline CI needs two things seeded

actions/checkout vendored into a local actions org, and Node in the image. Actions are JavaScript: without Node every workflow dies after resolving the action, which reads like a resolution failure and is not.

Two databases, and only two

PostgreSQL for Mattermost, MariaDB for BookStack. Neither has an alternative. Everything else is SQLite.

Some prose in data/schemas/ is stale

Parts of it still describe an earlier wiki and its authorship model; the world moved to BookStack. Where the schema prose and the code disagree, trust world/ and the ingest scripts.

Judge the artefact, not its summary

The clue gate once judged the one-clause condensation of a remark rather than the remark, and passed transcripts that had lost half of it. Whenever a check compares against a summary of a thing rather than the thing, ask what the summary drops — that is exactly what will go missing, and the check will report success.

12 — This pass

What the reorganization changed

Four commits, each revertible on its own, on top of a checkpoint of work that was already in the tree.

  1. The emitters moved to the pipeline that owns them. build_tasks.py, clue_digest.py, build_located_arm.py, refresh_answer_key.py and mail_register.py read task_generator/out/ and write into harbor_tasks/ — they are the authoring pipeline's last stage, not graded artifacts, and one of them already had to reach across sys.path to import the library it depends on. They now live in task_generator/.
  2. The retired t* material moved next to the tasks it grades. Eight dead suites were sitting in _suites/, which is copied wholesale into every arm, so all 80 live arms shipped suites for tasks nobody runs. They, the measurement record, the report generator and the two job configs now live in failed_tasks/ with the tasks themselves.
  3. Two traps the move exposed, fixed. A retired task would have emitted an arm whose tests/ had no suite in it — a collection error at verify time rather than an honest "this task has no suite"; and a bare build_tasks.py run defaulted to emitting seven arms nobody wanted.
  4. Deletions: a stray .rollouts/ at the repo root (the tool writes into the current directory, so one pull from the wrong place landed 13MB a level above the arms they describe), two stale one-off logs, an empty virtualenv, and two empty config directories.

It was proven rather than asserted. The emitters were run from two git worktrees — one at the commit before the move, one after — on nine tasks and every arm type. Stdout, stderr and the emitted trees came back byte-identical, and the only differences in the second run were the ten retired artifacts no longer being copied into 46 places. No file's contents differed anywhere, and all 80 arms still carry their own suite.

One thing was reported as a duplicate and is not. The two g4 hosted directories bind different server tasks — versions 5 and 7 — and both have pulled rollouts and validations; the rollout analysis points at the first. Neither was deleted. What they do share is one task name in their config, which is the actual bug and is worth fixing deliberately.
