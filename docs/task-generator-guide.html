SWEWorld · task_generator/

How task_generator makes a task

A pipeline that writes hidden-requirement coding tasks against the curator codebase, then proves that the hidden part really is hidden before any money goes on agent trials.

What it is

You write a short brief about one area of curator. The tool designs the whole feature, builds it, and only then cuts it in two: a ticket an agent is given, and hidden requirements it has to find. Then it builds the feature again from the ticket alone and checks, test by test, that the ticket-only build fails exactly where the hidden requirements are.

brief→whole spec→oracle build→ticket | hidden→tests→bracket→harbor task

A hidden-requirement task tests whether an agent working inside the SWEWorld company can find requirements that were never written into its ticket. Those requirements live in chat, the wiki and email. task_generator is the machine that makes such tasks verifiable. The words below come up on every other page of this guide.

brief
The one input you write by hand: 25–45 lines naming an area of curator, with exact files and line numbers.
whole.md
The complete specification, in parts, with nothing hidden yet.
ticket.md
The visible half, what every agent is given (“A” in the rubric).
hidden.md
The hidden half, usually two requirements, r1 and r2 (“B” and “C”).
fact
One gradable piece of a requirement, with a key like g1.r1.rule. Each requirement has up to five: rule, scope, exclusions_or_crossover, failure_behavior, observability. open_feature grades the ticket itself.
oracle / naive / spec
Three builds of the feature, each by a separate claude -p agent. The oracle builds from whole.md, naive from the ticket only, and spec from the ticket plus hidden.md.
bracket
The free, deterministic gate: one test suite run against every build, giving a verdict per fact.
arm
One version of the same task, differing only in what the agent is shown: blind, spec, clues or world.
clue · remark · herring
A clue is a planted remark in chat, wiki or mail that carries part of a fact. A herring is a decision the team made and later reversed, planted earlier.
plant · corpus
The plant is the ledger of placed remarks (clues/plant.json). The corpus is the company's generated chat, docs and mail it is written into.

Why it exists

The first 60 tasks (data_gen/input/tasks.json, now retired to failed_tasks/) were written ticket-first, with hidden requirements added afterwards. When those were measured, many “hidden” facts turned out to be ones an agent passed without ever seeing the clue, because the surrounding code already gave them away. Each of those was found only after a paid trial.

13 / 29facts in the hand-written tasks were coincidences, passed blind
~$1for a local ticket-only build that catches the same thing, against ~$7–9 for an agent trial
$19for task g2’s whole cut, spec 1.00 / blind 0.00, in one afternoon

The method comes from task_generator/rubric.md: design whole, then split. A requirement that was never separable from the visible ask can’t survive a split into ticket and hidden parts.

The pipeline

There are three phases. Each stage is one python3 task_generator/cli.py <stage> <slug> command. Every one writes a reviewable file under task_generator/out/<slug>/, so you can stop anywhere and read what came out.

A · The cut~$20, a few hours. Produces a gradable task.
brief (you)→ new→ author→ build oracle→ split→ tests→ build naive→ build spec→ bracket→ audit→ trim→ emit→ port grader
B · Measure~$7 and ~25 min per local trial, or hosted on Horizon.
trial --arm spec+ trial --arm blind→ report or horizon→ push · validate · evaluate
C · The plantOptional, ~$60–80, two thirds of the bill. Hides the requirements in the company.
clues→ settle→ reverse→ reorder→ reknit→ consistency→ prove --runs 3→ horizon→ inject
gate non-zero exit means look before continuing optional skipped unless you ask by hand the one input the tool can’t produce

Stage order, gates and budgets come from task_generator/tg/recipe.py. cli make <slug> --dry-run prints them next to what this task has actually spent. Phase B is listed before C because you can measure a task’s blind and spec arms before planting anything.

The bracket: how it knows a fact is hidden

This is the heart of the package. The four trees are the same curator checkout built from different inputs. One test suite runs against all four. Where each tree passes or fails tells you what each fact is really testing.

VerdictpristinenaiveoracleWhat it means · what to do
hiddenfailfailpassOnly someone who knew the requirement passes. Ship it.
coincidencefailpasspassThe ticket or the code gave it away. Run author --extend, not another split.
vacuouspasspasspassThe test doesn’t need the feature to exist. Fix the test.
broken——failThe reference build fails its own test. A real defect, so stop here.
unreachablefailfailpass · spec failsEven with the requirements in hand, a build fails. The requirement’s wording doesn’t say what the test grades.

The healthy shape is naive passing only open_feature: the agent built the feature from the ticket and recovered none of the hidden facts. If naive fails open_feature too, the ticket isn’t buildable. That is a gate as well, because a blind score of 0 would then mean “built nothing”, not “found nothing”.

The arms: one ticket, several conditions

Once a task is emitted, it can be run in several forms. In harbor_tasks/ each one is a sibling directory, like executor-output-cap-spec/. Only the information the agent is given changes, so the gap between arms is what’s being measured.

blindexpect ≈ 0.00

The ticket alone. A zero proves the requirements are really hidden, as long as open_feature is 1.0.

specexpect ≈ 1.00

Ticket plus the hidden requirements, stated outright. Proves the suite can be satisfied from what’s written.

cluesthe ceiling

Ticket plus every planted remark, quoted inline in date order. Can an agent use scattered evidence once it has been gathered for it?

worldthe real test

The blind ticket, run inside a baked SWEWorld image whose chat, wiki and mail contain those same remarks among everything else. Can the agent find them?

world-locatedsplits the miss

The world arm, told which pages and days hold the evidence. Separates “couldn’t find it” from “found it and didn’t use it”.

…-hostedfor Horizon

The same world arms, built from the published registry image, because Horizon can’t resolve a local image tag.

Rewards are folded by harbor_tasks/_suites/score.py, the same module the paid verifier uses. So g1.r1.rule means the same thing in a local bracket, a Harbor trial and a Horizon rollout. reward is the mean over hidden facts and leaves out open_feature.

How to read the ladder: clues matching spec means the plant is sufficient and any blind gap is retrieval. clues matching blind means the plant is too thin, and no amount of corpus work will fix it.

Before you start

Run everything from the repo root. Define this once per shell:

cli() { python3 task_generator/cli.py "$@"; }
  • The devbox container is running, from image sweworld:repo-only-dev (built from harbor_tasks/_env/Dockerfile).curator can’t be imported on the host. Every test run goes through docker exec devbox, using /opt/curator-dev/venv. Check with docker ps.
  • The curator/ checkout exists at the repo root.Builds copy it into .trees/ or a temp directory. Never edit it directly.
  • The claude CLI works on your subscription: CLAUDE_CODE_OAUTH_TOKEN in .env.tg/auth.py removes ANTHROPIC_API_KEY from every agent’s environment. If the token is missing, the tool refuses to run rather than falling back. Quick test: claude -p 'say ok'.
  • For the plant only: a phase-4 corpus at data_gen/build/phase4/runs/latest.The clue stages place remarks into conversations that already exist.
  • For hosted runs only: ~/horizon_env/bin/horizon, plus HORIZON_API_KEY and MINI_BATCH_ID.It isn’t on PATH. Export PATH="$HOME/horizon_env/bin:$PATH" first.

Build your first task, step by step

There is a one-shot cli make <slug>, but no task has actually been built with it. split and bracket exit non-zero on heuristics, and make can’t tell a warning from a real defect. Walk the stages one at a time, and read the one thing listed before typing the next command.

stop on fail a real defect advisory exit non-zero is a prediction, so read it by hand your judgement

  1. Pick an area and write the brief

    by hand~15 min reading curator

    This is the one input the tool can’t produce, and it decides whether the task works. Look for two parts of the code that disagree, where the disagreement matters. For example, g2 had three exit paths assembling output independently, and two result types disagreeing about whether a stream may be absent.

    Use the shape of task_generator/out/*/brief.md: the area in one sentence, then The area, concretely: with exact files and line numbers, then the disagreement in plain words, then Constraints:. The constraints should say: pure, deterministic, no network, no sleeping, no threads, clock and randomness injected, and which fakes the tests may use.

    • Prefer a behaviour change inside existing shapes over a brand-new module with an exact public API. Blind agents build the first far more often.
    • Avoid code that starts a live display, a pager or a terminal takeover when constructed. It has killed agents’ shells mid-rollout.
    • An area with one obvious implementation gives facts a blind agent passes for free.

  2. Scaffold it

    free
    cli new my-area --brief "$(cat brief.txt)"
cli make my-area --dry-run   # the stage table and what's left to spend
    Writes
    out/my-area/brief.md and a skeleton task.json. The id is the next free g<N>, so the suite becomes g<N>_my_area.
    Read
    Check that the id and suite are what you expected. Everything downstream, including harbor_tasks/, keys off them.

  3. Author the whole specification

    ~$6
    cli author my-area
    Writes
    whole.md: the feature in parts, each naming alternatives an engineer could plausibly pick instead.
    Read
    For each part, ask: could a competent engineer reach this just by reading the ticket and the source? If yes, it isn’t hidden. At least half the parts should carry something the codebase can’t supply: an invented name, a chosen value, a policy with no local evidence, or a deliberate departure from what the code does now.

  4. Build the oracle

    ~$3.50
    cli build my-area --role oracle
    Writes
    A working tree at .trees/my-area/oracle/, frozen as fixtures/oracle.{patch,py}.
    Read
    Nothing yet. The bracket judges the oracle, not you.

  5. Split into ticket and hidden requirements

    ~$1.30advisory exit
    cli split my-area
    Writes
    ticket.md, hidden.md, task.json and fact_sources.json. Earlier cuts are archived in cuts/cut-N/. It re-cuts once by itself if the ticket leaked a name a fact needs.
    Read
    The anchor audit it prints (tg/leak.py): identifiers each fact relies on that neither the ticket nor the source tree already contains. Exit 1 means “some fact has no invented name”. That is a prediction, not a verdict, because a fact can rest on a chosen value instead.

  6. Write the tests

    largest per-call budgetstop on fail
    cli tests my-area
    Writes
    tests/test_open.py, test_r1.py and test_r2.py: one decisive test per fact, all passing on the oracle.
    Read
    What each test reaches for, because that is what actually gets graded. A test that reads a path outside /workdir, /tests or /tmp passes locally and scores 0 hosted. g3 did exactly this.

  7. Build naive and spec

    ~$2 each
    cli build my-area --role naive   # sees ticket.md only
cli build my-area --role spec    # sees ticket + hidden.md
    Writes
    fixtures/naive.patch and fixtures/spec.patch, built in isolated temp directories.
    Why both
    The oracle shares the author’s assumptions. Only a build from the requirement text alone shows whether that text is enough. g3’s spec arm capped at 0.44 for lack of this.

  8. Run the bracket

    free · ~1 minthe gate
    cli bracket my-area
    Writes
    bracket.json and bracket.md, with a verdict per fact.
    Read
    Every fact should read hidden. broken or unreachable means stop and fix. For coincidence, run cli author my-area --extend, then rebuild and re-bracket. Naive is built once, so a single coincidence is one noisy sample. Treat several as a verdict on the specification.

  9. Trim, then emit

    ~$3 · freeemit refuses unless shipped
    cli audit my-area      # optional adversarial review; skipping is a choice
cli trim my-area       # cut each requirement to what its tests check
cli bracket my-area    # again: trim changed what spec is handed
cli emit my-area
    Writes
    harbor_tasks/g<N>-my-area/, harbor_tasks/_suites/g<N>_my_area/, and this task’s row in task_generator/tasks.generated.json.
    Checks
    emit.check_bijection: every fact has a test, and every test has a fact.

  10. Port the grader to worker and judge

    by hand, for now

    cli tests writes plain pytest files, and on that path the process that imports the agent’s code also writes the result file. An agent’s code can rewrite that result from an atexit hook, and this was measured at reward 1.0 from an untouched tree. Every shipped task from g1 to g11 was then ported to a two-process grader:

    • probe.py imports the submission as user nobody, inside a jail that can’t read /tests, and records only raw values.
    • judge.py runs as root, never imports agent code, and applies the assertions. It writes the same test ids, so scoring is unchanged.
    Writes
    harbor_tasks/_suites/<suite>/probe.py, probe_support.py and judge.py. run_suites.py switches to the split only when both files exist.
    Recipe
    §7 of tasks/grading-forgery-fix-handoff.md. Read its “Round 4” section first, which supersedes the earlier file-lock approach. Verify with oracle 1.0 and noop 0.0 before pushing.

    You now have a gradable task. Go to Measure it, or continue to the plant to hide its requirements in the company.

Hide it in the world (the plant)

So far the hidden requirements exist only in hidden.md. The plant turns each one into remarks scattered across months of chat, wiki and mail, placed into conversations that already exist in the generated corpus. That is what the clues and world arms need. Unlike data_gen/phase3_plant.py, which plants before simulation, this plants after, into a finished corpus.

# long stages: run detached, not just backgrounded
setsid nohup python3 task_generator/cli.py clues my-area > clues.log 2>&1 < /dev/null &
StageBudgetWhat it does
clues~$45Builds a tree of subconclusions and leaf remarks per requirement, writes herrings, and places each leaf in a real chat day, wiki page, comment or mail thread. About 175 placement calls.
settle~$11Checks every test assertion against the remarks as stated / implied / absent, and rewrites remarks so that “implied” becomes “stated”.
reverse~$1Makes sure someone later says out loud that each herring’s decision was dropped.
reorder~$1Moves any decision dated before the complaint it answers. Must run before reknit.
reknit~$9Turns each remark into a real multi-turn exchange. No single turn carries the whole remark, and every identifier is still typed literally.
consistency~$8Catches a fact that an exchange ended up stating backwards.
prove --runs 3~$5.50Builds from ticket plus remarks alone, three times, and scores with the real suite. Facts that fail together on the same runs point to one bad remark. Fix it with cli repair.
horizon --arms blind,spec,cluesfreeRenders the hosted task directories. It refuses a clues arm whose remarks never type a graded name.
injectfreeWrites the plant into a copy of the corpus, for re-baking the world image (the world arm).

After the plant, build the arms that use it:

python3 task_generator/build_tasks.py --extra-tasks task_generator/tasks.generated.json \
    --pick g<N> --world --hosted                         # blind, spec, clues, world (+ hosted)
python3 task_generator/build_located_arm.py my-area        # -world-located
cli answers my-area                                        # the task's answer-key README

For the world arm, cli inject first, then data_gen/install_corpus.py, then make bake-image TAG=<next>, then point WORLD_IMAGE in build_tasks.py at the new tag. Rebuild after every re-plant, because build_tasks.py rewrites each arm’s tests/ and plant/ wholesale.

Each paid clue pass checkpoints to .{stamp}.partial.json, so a killed run loses one call, not the whole pass. cli snap <slug> <label> snapshots the plant before a risky change.

Measure it

Locally, first

cli trial my-area --arm spec    # ~25 min, ~$7 — should be ≈ 1.00
cli trial my-area --arm blind   # should be ≈ 0.00, with open_feature at 1.0
cli trial my-area --arm clues   # after the plant
cli report my-area              # → out/my-area/report.md

Those two numbers are the verdict: spec ≈ 1.00 says the suite can be satisfied, and blind ≈ 0.00 says the requirements are really hidden. If several facts fail together with identical assertion errors, that is one defect, usually one ambiguous sentence, not variance.

Hosted, on Horizon

cli horizon my-area --arms blind,spec,clues
export PATH="$HOME/horizon_env/bin:$PATH"
cd task_generator/out/my-area/horizon

horizon tasks push g<N>-my-area                      # blind arm
horizon tasks push g<N>-my-area-spec                 # spec arm
horizon tasks validate --mode hosted --agent oracle  # must be 1.00
horizon tasks validate --mode hosted --agent noop    # must be 0.00
horizon tasks validate-logs

horizon evaluations submit --model biggie-max --runs 3 <task-id>
horizon evaluations watch <eval-id>
horizon rollouts pull <task-uuid>

Hosted oracle/noop validation is the same bracket, in Horizon’s terms. New tasks are limited to cipher-omni until 10+ rollouts land below a 0.4 pass rate. Until then biggie-max returns 403. These apex arms use agent type meteor. The harbor-format -world* arms use typhoon.

When a step comes out wrong, open logs/<step>.prompt.md. It is exactly what the model was told, so you can diagnose from it instead of re-running.

Pitfalls worth knowing

Don’t re-cut on coincidences.

Re-running split only changes which parts are hidden. It cost g2 about $6 and changed nothing. A coincidence is a fact about the specification, so run author --extend. Re-cut only when the ticket leaked a name.

Run long stages detached.

Use setsid nohup … < /dev/null &. Many plant stages run past ten minutes, which is where harnesses tend to kill child processes.

Auth goes the wrong way silently.

If both the API key and the OAuth token are set, the CLI prefers the key. tg/auth.py strips the key for you. Never pass --bare.

open_feature is graded but not in the reward.

If a ticket-only build can’t pass it, a blind 0.00 is meaningless. Fix it by amending the ticket in task.json and ticket.md, not by re-splitting.

Horizon’s status table misleads during a run.

Unfinished rollouts show as failed. Use evaluations watch for progress and status --json for the truth. g4’s evaluation was cancelled over this, costing $17.

Shared-state hazards if you run several tasks.

cli new picks the next id by scanning, so pass --id. emit rewrites all of tasks.generated.json, so take fleet/locks/generated.lock.

Going further

  • cli make <slug> --from <stage> resumes the recipe from a stage once you know an area’s gates behave. --optional also runs audit and inject.
  • fleet/orchestrate.py drives several tasks at once through the same cli.py commands. It adds locks, a gate reader, and a judge that makes the calls this guide leaves to you (extend vs re-cut, advisory vs fatal). Start with orchestrate.py start --dry-run --ids g7,g8 and orchestrate.py verify.
  • harbor_tasks/README.md describes the emitted arm ladder and how to run one with harbor run -p harbor_tasks/g<N>-<slug>. Point it at one task folder: -p harbor_tasks on its own runs nothing.
  • Other commands are answers to something a gate printed: repair fixes remarks a proof blamed, replace re-places remarks with the same wording, resync brings the plant back in line after a corpus edit, and answers writes the answer key. suite and exec are how the build agents run code, and aren’t meant to be typed by hand.
  • The full manual is task_generator/README.md. It includes the history behind each rule, like g1’s two cuts and g2’s cost breakdown.
