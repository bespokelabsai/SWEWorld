# Hidden requirements — g8 (attachment-payload)

## r1
- **rule** — The base processor owns a per-kind size ceiling that is enforced inside `_canonical_attachment_block` BEFORE `self.file_upload_limit_check(payload)` is invoked: the base64 payload is measured once with `file_utilities.get_base64_size(payload)` and compared against `_ATTACHMENT_SIZE_LIMIT_MB = {"image": 20.0, "document": 24.0}`; strictly greater (`>`) rejects, exactly at the limit passes. The limit is selected by the block's `kind`, so a document-MIME attachment gets 24.0 and an image-MIME attachment gets 20.0 regardless of the Python class it arrived as.
- **scope** — The ceiling lives once in `BaseOnlineRequestProcessor` and therefore applies identically to the openai, anthropic and litellm paths; it does not replace the per-provider `file_upload_limit_check` hooks, which still run afterwards for base64 payloads and whose own rejections propagate unchanged. Only `source == "base64"` attachments are measured: a URL attachment is not fetched, not measured, not rejected as unmeasurable, carries `size_mb is None`, and is never handed to the provider hook.
- **exclusions_or_crossover** — A whole-prompt aggregate ceiling `_ATTACHMENT_PROMPT_LIMIT_MB = 45.0` also exists and is NOT a per-attachment rule: `_handle_multi_modal_prompt` converts every attachment in the prompt first (so every per-attachment check and every `file_upload_limit_check` call for the whole prompt has already happened), then sums `block.size_mb` over the `source == "base64"` blocks only and rejects when that total is strictly greater than 45.0. It is never evaluated incrementally, so no attachment is skipped once the running total crosses the line, and the reported size is the whole-prompt total. URL blocks contribute nothing to the sum.
- **failure_behavior** — Both rejections raise `AttachmentTooLarge(kind, size_mb, limit_mb)`, a subclass of `AttachmentError`, exposing `.kind`, `.size_mb` and `.limit_mb` as attributes. `.kind` is the block kind (`"image"` or `"document"`) for a per-attachment rejection and the literal `"prompt"` for the aggregate rejection. Nothing is truncated, downsampled, dropped or warned-and-passed-through.
- **observability** — With a stub whose `file_upload_limit_check` raises `RuntimeError("provider")` unconditionally: `Image(content="A" * 33_554_432)` (24.0 MB base64) raises `AttachmentTooLarge` — not `RuntimeError` — with `exc.kind == "image"`, `exc.size_mb == 24.0`, `exc.limit_mb == 20.0`; the same 24.0 MB payload on a PDF-MIME attachment (`kind == "document"`) passes the base check and reaches the hook, so `RuntimeError` is raised. With a recording stub, a `_MultiModalPrompt` of three `Image(content="A" * 25_165_824)` (18.0 MB each) followed by one `Image(content="A" * 8_388_608)` (6.0 MB) raises `AttachmentTooLarge` with `exc.kind == "prompt"`, `exc.size_mb == 60.0`, `exc.limit_mb == 45.0` AND `len(stub.calls) == 4`; the first two of those images alone yield a 2-block content list, `len(stub.calls) == 2`, no exception. A remote-URL attachment leaves `stub.calls == []` and `block.size_mb is None`.
- **$comment** — 
- *earlier, reversed*: An earlier build short-circuited the aggregate as soon as the running total crossed the line; it was reversed because the reported size and the number of provider-hook calls then depended on attachment ordering.

## r2
- **rule** — `_canonical_attachment_block` refuses an attachment whose MIME could not be resolved instead of substituting a fallback: when the resolved `mime_type` is `None` it raises `UnknownAttachmentMimeType(url=data.url, attachment_type=data.type)`, a subclass of `AttachmentError`. `attachment_type` carries the `BaseType.type` ClassVar vocabulary — `"image"` or `"file"` — not the block `kind` vocabulary. The refusal happens when the block is built, not when the model is constructed, so `Image(url=...)` / `File(url=...)` themselves never raise for a missing MIME.
- **exclusions_or_crossover** — `BaseType.is_remote` is true only when `url` starts with `http://` or `https://` (case-insensitive); that is the whole definition of remote. Any other scheme — `s3://`, `gs://`, `file://`, `data:` — is treated as a local filesystem path and must exist, so `File(url="s3://bucket/report.pdf")` is a missing-attachment rejection rather than a URL-sourced block. An attachment carrying inline `content` and no `url` is exempt from the existence check entirely.
- **failure_behavior** — A non-remote `url` that does not exist on disk raises `MissingLocalAttachment(url=data.url)`, also a subclass of `AttachmentError`, exposing `.url` — it is not shipped to the provider as `{"url": "/tmp/typo.png"}` and not silently skipped. This existence check runs BEFORE the MIME resolution check, so a path that is simultaneously missing and unguessable reports the missing file: `File(url="/tmp/definitely-missing/notes")` raises `MissingLocalAttachment`, not `UnknownAttachmentMimeType`.
- **observability** — `StubOnline()._canonical_attachment_block(File(url="https://example.com/download"))` raises `UnknownAttachmentMimeType` with `exc.url == "https://example.com/download"`, `exc.attachment_type == "file"`, `isinstance(exc, AttachmentError)` and `isinstance(exc, ValueError)`; the `Image` equivalent gives `exc.attachment_type == "image"`; constructing `File(url="https://example.com/download")` on its own raises nothing. `_canonical_attachment_block(Image(url="/tmp/definitely-missing/typo.png"))` raises `MissingLocalAttachment` with `exc.url == "/tmp/definitely-missing/typo.png"`. In every rejection the provider hook was never reached, so `stub.calls == []`.
- **$comment** — 
- *earlier, reversed*: An earlier revision validated MIME resolution at model construction with a pydantic validator; it was reversed because building an `Image`/`File` for a provider that never needs the MIME then failed.
