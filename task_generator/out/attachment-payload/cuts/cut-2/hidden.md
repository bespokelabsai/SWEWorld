# Hidden requirements — g8 (attachment-payload)

## r1
- **rule** — Attachment size ceilings live in the base processor, not in the providers. Two module-level constants in the new attachment module: `_ATTACHMENT_SIZE_LIMIT_MB: dict[str, float] = {"image": 20.0, "document": 24.0}` and `_ATTACHMENT_PROMPT_LIMIT_MB: float = 45.0`. Every base64 attachment is measured once with `bespokelabs.curator.file_utilities.get_base64_size(payload)` (MB) while its canonical block is built, the measurement is stored on the block as a seventh field `size_mb: float | None = None`, and a measurement strictly greater than `_ATTACHMENT_SIZE_LIMIT_MB[kind]` raises a new `AttachmentTooLarge(AttachmentError)` whose `__init__(self, kind: str, size_mb: float, limit_mb: float)` stores `.kind`, `.size_mb`, `.limit_mb` and whose message is `f"{kind} attachment is {size_mb} MB, over the {limit_mb} MB limit."`. Separately, after every attachment of a `_MultiModalPrompt` has been converted to a block, `_handle_multi_modal_prompt` sums `size_mb` over the `source == "base64"` blocks and raises `AttachmentTooLarge(kind="prompt", size_mb=<sum>, limit_mb=45.0)` when the sum is strictly greater than 45.0.
- **scope** — The per-attachment ceiling is keyed on the block `kind` resolved from the MIME type, not on the Python class: the same 24.0 MB base64 payload is rejected as an `"image"` (limit 20.0) and accepted as a `"document"` (limit 24.0, strict `>`). Only `source == "base64"` blocks are measured; a `source == "url"` block is not sized at all and carries `size_mb is None`, contributing nothing to the prompt sum. The aggregate check belongs to `_handle_multi_modal_prompt` only; a single call that builds one block never applies it.
- **exclusions_or_crossover** — The base ceiling runs before the existing per-provider hook `self.file_upload_limit_check(payload)`, which is still called for every base64 payload that the base ceiling accepted — so the hook only ever sees accepted payloads, and a stub hook that raises unconditionally is never reached by an oversized image. A remote-URL attachment is never offered to `file_upload_limit_check` at all.
- **failure_behavior** — `AttachmentTooLarge` subclasses the attachment error base (and therefore `ValueError`). `Image(content="A" * 33_554_432)` (a 24.0 MB base64 payload) raises it with `exc.kind == "image"`, `exc.size_mb == 24.0`, `exc.limit_mb == 20.0` — and not the provider hook's error. `Image(content="A" * 33_554_432, mime_type="application/pdf")` clears the base check and reaches the provider hook instead.
- **observability** — A prompt of four images — three `Image(content="A" * 25_165_824)` (18.0 MB each) then one `Image(content="A" * 8_388_608)` (6.0 MB), each individually under 20.0 MB — raises `AttachmentTooLarge` with `exc.kind == "prompt"`, `exc.size_mb == 60.0`, `exc.limit_mb == 45.0`, and a recording stub hook shows all four payloads were offered (four calls), proving the sum is taken over the finished prompt rather than incrementally. Control: the first two images alone (36.0 MB) yield a two-block content list, two hook calls, no exception.
- *earlier, reversed*: The first cut used a single flat 20 MB ceiling for every attachment and let `file_upload_limit_check` run first; it was reversed after PDFs between 20 and 24 MB were rejected by the wrong error and the provider hook's message leaked instead of the base one.

## r2
- **rule** — `openai_request_mixin.py` gains a module-level `_OPENAI_TOKENS_PER_DOCUMENT = 1400`, and `calculate_input_tokens` charges exactly that flat cost for a document-bearing block, independent of the block's payload size.
- **scope** — The 1400-token cost applies to both spellings of a document block — the OpenAI-shaped `{"type": "file", "file": {...}}` and the Anthropic-shaped `{"type": "document", "source": {...}}`. Image blocks in both spellings (`"image_url"` and `"image"`) keep the existing `_OPENAI_TOKENS_PER_IMAGE["low"]` cost of 85, and text blocks keep the encoder-derived cost.
- **failure_behavior** — A block whose `"type"` is none of `text`/`image_url`/`image`/`file`/`document` — e.g. `{"type": "thinking", "thinking": "ignored"}` — contributes 0 tokens and raises nothing; the function does not reject or log unrecognised block types.
- **observability** — With a 1-token-per-character encoder and the content list `[text "hello", an `image_url` block, an anthropic `image` block, a `file` block, a `document` block, a `thinking` block]`, `calculate_input_tokens` returns exactly `5 + 85 + 85 + 1400 + 1400 + 0 == 2975`. End to end, the three-block content of one remote JPEG, one local PDF and the text `"Summarise these"` costs `85 + 1400 + 15 == 1500`.
- *earlier, reversed*: Documents were first priced with the Anthropic constants already in the tree (1024 per image, 2048 per document); that was reversed to a flat 1400 per document with images left at 85 after the estimate ran consistently high on mixed prompts.
