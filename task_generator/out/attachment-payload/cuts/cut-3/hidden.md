# Hidden requirements — g8 (attachment-payload)

## r1
- **rule** — The base owns four refusals that no provider can waive, all defined in `attachment.py`. (a) Per-kind byte ceiling: every base64 payload is measured exactly once with `bespokelabs.curator.file_utilities.get_base64_size(payload)` and compared against `_ATTACHMENT_SIZE_LIMIT_MB: dict[str, float] = {"image": 20.0, "document": 24.0}`; strictly greater is a refusal. The measured value is kept on the block as an additional field `size_mb: float | None = None`. (b) Whole-prompt aggregate: `_ATTACHMENT_PROMPT_LIMIT_MB: float = 45.0`; the sum of `size_mb` over the base64 blocks of one `_MultiModalPrompt`, strictly greater than 45.0, is a refusal, and the sum is taken once after every block in the prompt has been built. (c) Count cap: `_ATTACHMENT_COUNT_LIMIT: int = 12`; `len(message.attachments())` strictly greater than 12 is a refusal, evaluated before a single block is built. (d) Empty payload: a `source == "base64"` attachment whose `serialize()` returns `""` is a refusal.
- **scope** — The per-kind ceiling and the empty-payload check live in `_canonical_attachment_block`; the count cap and the 45.0 MB aggregate live in `_handle_multi_modal_prompt` alone, so `_canonical_attachment_block` and `_format_multimodal` never apply either. The order inside `_canonical_attachment_block` is exactly: `MissingLocalAttachment`; `UnknownAttachmentMimeType`; derive kind/detail/filename and return here for a remote attachment; `payload = data.serialize()` then the empty-payload refusal; then the per-kind ceiling; then `self.file_upload_limit_check(payload)`; then the frozen block. The base ceiling therefore runs before the provider hook, which only ever sees payloads the base already accepted.
- **exclusions_or_crossover** — A `source == "url"` block is never measured or read: its `size_mb` is `None`, it contributes nothing to the 45.0 MB sum, and it can never be empty. `texts` are not counted against the 12-attachment cap. Documents are held to 24.0 MB rather than 20.0 MB, so one and the same 24.0 MB base64 payload is refused when `kind == "image"` and accepted (reaching the provider hook) when `kind == "document"`.
- **failure_behavior** — `AttachmentTooLarge(AttachmentError)` with `__init__(self, kind: str, size_mb: float, limit_mb: float)` storing `.kind`, `.size_mb`, `.limit_mb`, message `f"{kind} attachment is {size_mb} MB, over the {limit_mb} MB limit."` — `kind` is the block kind for the per-attachment ceiling and the literal `"prompt"` for the aggregate. `TooManyAttachments(AttachmentError)` with `__init__(self, count: int, limit: int)` storing `.count`, `.limit`, message `f"Prompt has {count} attachments, over the limit of {limit}."`. `EmptyAttachment(AttachmentError)` with `__init__(self, url: str, filename: str)` storing `.url`, `.filename`, message `f"Attachment {filename} has an empty payload: {url!r}"`. All are `AttachmentError` and therefore `ValueError` subclasses.
- **observability** — With a stub whose `file_upload_limit_check` appends its argument to `stub.calls`: four images of 18.0/18.0/18.0/6.0 MB base64 (each individually under 20.0) raise `AttachmentTooLarge` with `.kind == "prompt"`, `.size_mb == 60.0`, `.limit_mb == 45.0` and `len(stub.calls) == 4` — the whole prompt was built before the refusal, not abandoned when the running total crossed 45.0 at the third image; the first two of those images alone give a 2-block content list with `len(stub.calls) == 2`. Thirteen copies of `Image(content=b"x")` raise `TooManyAttachments` with `.count == 13`, `.limit == 12` and `stub.calls == []`; twelve give a 12-block list with `len(stub.calls) == 12`; `_MultiModalPrompt(texts=["a"] * 40, images=[tiny])` returns 41 blocks and raises nothing. With a stub whose hook raises `RuntimeError`, `Image(content="A" * 33_554_432)` raises `AttachmentTooLarge(.kind == "image", .size_mb == 24.0, .limit_mb == 20.0)` while the same payload with `mime_type="application/pdf"` raises `RuntimeError`. A zero-byte `tmp/empty.pdf` raises `EmptyAttachment` with `.filename == "empty.pdf"` and `stub.calls == []`, while a zero-byte extension-less `tmp/scratch` raises `UnknownAttachmentMimeType` instead.
- *earlier, reversed*: The aggregate was first checked incrementally, raising as soon as the running total crossed 45.0 MB so trailing attachments were never serialized; it was reversed to a single post-build sum so the reported size_mb is the whole prompt's total.

## r2
- **rule** — `attachment.py` also owns three derived values that `_canonical_attachment_block` computes rather than copies. (a) `_ATTACHMENT_FINGERPRINT_HEX_LEN: int = 12` and a pure `attachment_fingerprint(payload: str) -> str` returning `"sha256:" + hashlib.sha256(payload.encode("utf-8")).hexdigest()[:12]`; `AttachmentBlock` gains a required field `fingerprint: str`, set from the block's payload for both sources. (b) `_MAX_ATTACHMENT_FILENAME_LEN: int = 64`: a derived filename longer than 64 characters becomes `name[: 64 - len(ext)] + ext` where `ext = os.path.splitext(name)[1]`, so the result is exactly 64 characters and keeps its extension; when `len(ext) >= 64` the name is simply cut to its first 64 characters; 64 or fewer is untouched. (c) `_SUPPORTED_IMAGE_DETAILS: tuple[str, ...] = ("auto", "low", "high")` and a pure `normalize_detail(value: str | None) -> str` returning `str(value).strip().lower()` when that lands in `_SUPPORTED_IMAGE_DETAILS` and `"auto"` otherwise; an image block's `detail` is `normalize_detail(getattr(data, "detail", "auto"))`.
- **scope** — All three happen at block-build time, inside `_canonical_attachment_block`, and touch only the `AttachmentBlock`: `Image.detail` keeps whatever raw string the caller wrote, `data.url` is never rewritten, and `block.payload` keeps the full untruncated URL or base64 text. The fingerprint of a `source == "url"` block is taken over the URL string exactly as given, query and fragment included; the digest is always over the payload *string*, never over decoded bytes, and never over the other block fields.
- **exclusions_or_crossover** — None of this metadata reaches a provider: `_render_openai_block` and `_render_anthropic_block` still compare `==` to the dicts the ticket tabulates, so no `"fingerprint"` and no `"size_mb"` key appears in an `image_url`, `file`, `image` or `document` block — what the OpenAI `file` block carries is the capped `filename` beside the full untruncated `file_url`, and what its `image_url` block carries is the normalized `detail`. A document block keeps `detail is None` and is never given a normalized detail.
- **failure_behavior** — An unsupported detail string is downgraded, not rejected and not passed through: `Image(content=b"x", detail="ultra")` builds a block with `detail == "auto"` and emits exactly one `logger.warning`; a supported value emits none, and `normalize_detail(None) == "auto"` with no warning. Constructing the `Image` itself never raises for an unknown detail.
- **observability** — `attachment_fingerprint("JVBERi0xLjQK") == "sha256:fc1c4358d4aa"`; for `tmp/report.pdf` holding `b"%PDF-1.4\n"`, `stub._canonical_attachment_block(File(url=str(tmp / "report.pdf"))).fingerprint == "sha256:fc1c4358d4aa"`; `Image(url="https://cdn.example.com/photos/cat.jpeg?size=large")` gives `.fingerprint == "sha256:80ce7facd006"` and `Image(content=b"x")` gives `"sha256:5e21d86b709b"`. `File(url="https://cdn.example.com/reports/2024-q4-consolidated-financial-statements-and-notes-final-approved-v3.pdf")` renders as `{"type": "file", "file": {"filename": "2024-q4-consolidated-financial-statements-and-notes-final-ap.pdf", "file_url": <the full 73-character-basename URL>}}`; a basename of exactly 64 characters passes through unchanged; a 72-character extension-less basename yields `"ledger-entries-consolidated-2024-q4-final-copy-for-review-board-"`. `b(Image(content=b"x", detail="HIGH")).detail == "high"`, `b(Image(content=b"x", detail=" Low ")).detail == "low"`, `b(Image(content=b"x", detail="ultra")).detail == "auto"`, and `_render_openai_block(b(Image(content=b"x", detail="HIGH")))` equals `{"type": "image_url", "image_url": {"url": "data:image/png;base64,eA==", "detail": "high"}}`.
- *earlier, reversed*: The fingerprint was first taken over the decoded bytes with url blocks left unfingerprinted; it was reversed to hashing the payload string so a url block has an id too.
