# Hidden requirements — g12 (backend-params-config)

## r1
- **rule** — The offending-key report is aggregate and name-based: `BackendParamError.params` is a tuple of every supplied key that is not in `_MODE_CONFIGS[mode].model_fields`, sorted ascending by `str` (not caller insertion order, not just the first offender). `belongs_to` is built by iterating the other config classes in the fixed order `BatchRequestProcessorConfig`, `OnlineRequestProcessorConfig`, `OfflineRequestProcessorConfig` and keeping each whose `model_fields` contains *every* offending key — intersection, not union — with membership decided by field name only; no other config class is ever constructed or asked to validate the values. When no class declares all of them, `belongs_to == ()`.
- **exclusions_or_crossover** — The neighbouring case must not get this treatment: when every supplied key is a field of the mode's config class but a value is bad, the `pydantic.ValidationError` raised by the constructor propagates unchanged — not caught, not wrapped in `BackendParamError`, not converted to the old friendly `ValueError`. So `{"model": "gpt-4o", "max_retries": -1}` with `batch=True` raises a plain `ValidationError` with exactly one error at `loc == ("max_retries",)`, and `isinstance(exc, BackendParamError)` is False.
- **failure_behavior** — Ordering inside `_validate_backend_params`: `None`-valued entries are dropped from a copy of `params` first (the caller's dict is not mutated and the corresponding fields fall back to their declared defaults), then the unknown-key scan runs, then the config class is constructed. Consequences: a dict carrying both an unknown key and an invalid value raises `BackendParamError` naming only the unknown key, and a wrong-mode key whose value is `None` raises nothing at all.
- **observability** — `_validate_backend_params({"model": "gpt-4o", "batch_size": "auto"}, batch=False)` raises `BackendParamError` with `params == ("batch_size",)` and `belongs_to == ("BatchRequestProcessorConfig", "OfflineRequestProcessorConfig")` — the offline class is listed even though `"auto"` is not a legal value for its `int` field. `_validate_backend_params({"model": "gpt-4o", "tensor_parallel_size": 2, "batch_size": "auto", "nope": 1}, batch=False)` gives `params == ("batch_size", "nope", "tensor_parallel_size")` and `belongs_to == ()`. `_validate_backend_params({"model": "gpt-4o", "batch_size": 8, "max_retries": -1}, batch=False)` gives `params == ("batch_size",)`. `_validate_backend_params({"model": "gpt-4o", "max_retries": None}, batch=True).max_retries == 10`, and `{"model": "gpt-4o", "batch_size": None, "max_requests_per_minute": None}` with `batch=False` returns an `OnlineRequestProcessorConfig` without raising and leaves the input dict with all three keys.
- *earlier, reversed*: An earlier iteration decided `belongs_to` by actually calling `OtherClass.model_validate(params)` and listing the classes that succeeded; it was reversed after that made the list value-sensitive and dropped `OfflineRequestProcessorConfig` from the `batch_size="auto"` report.

## r2
- **rule** — The base config's replacement `model_post_init` records unsupported generation params instead of rejecting them: it looks up `litellm.get_supported_openai_params(model=self.model)` and assigns `self.unsupported_generation_params = tuple(sorted(k for k in self.generation_params if k not in supported))`. The field is declared on `RequestProcessorConfig` as `unsupported_generation_params: tuple[str, ...] = Field(default=(), exclude=True)`. An unsupported generation param never raises.
- **scope** — Applies to `RequestProcessorConfig` and therefore to the batch and online configs. `OfflineRequestProcessorConfig` overrides `model_post_init` to set the value to `()` unconditionally, without importing or calling litellm.
- **failure_behavior** — The lookup is defensive: if `get_supported_openai_params` returns `None` or raises any `Exception`, `unsupported_generation_params` is `()` and nothing propagates out of construction.
- **observability** — With `litellm.get_supported_openai_params` patched to return `["temperature", "max_tokens"]`, `OnlineRequestProcessorConfig(model="gpt-4o", generation_params={"top_k": 1, "temperature": 0.5, "frobnicate": 2})` constructs and has `unsupported_generation_params == ("frobnicate", "top_k")`, while the same call on `OfflineRequestProcessorConfig` gives `()`; patched to raise or to return `None`, the online one also gives `()`. `"unsupported_generation_params" not in c.model_dump()`. Because it is a real field, `_validate_backend_params({"model": "gpt-4o", "unsupported_generation_params": ("x",)}, batch=True)` raises no `BackendParamError` and returns a config whose value has been overwritten with `()`.
- *earlier, reversed*: The team first shipped the faithful repair — rename to `model_post_init` and raise `ValueError(f"Generation parameter '{key}' is not supported for model '{self.model}'")` per offending key — and reversed it after litellm's supported-params table proved stale for newly released models.
