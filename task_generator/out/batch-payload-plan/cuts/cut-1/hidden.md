# Hidden requirements — g1 (batch-payload-plan)

## r1
- **rule** — A row's planned size is the byte length of the provider-specific request dict, not of the GenericRequest written to requests_*.jsonl: `measure_request_payload(generic_request)` returns `payload_size_bytes(self.create_api_specific_request_batch(generic_request))` — the very dict `create_batch_file` serialises. For the OpenAI processor with model `gpt-4o-mini`, no response_format and no system prompt, prompt func returning `row["prompt"]`, and row `{"prompt": "say 0"}`, `measure_request_payload(req) == 153` (measuring the generic request gives 217, the JSONL line gives 218), and for a 5-row dataset of such rows `plan_request_batches(dataset)[0].num_bytes == len(create_batch_file(those api-specific requests))`.
- **scope** — `plan_request_batches` computes `generation_params_per_row = "generation_params" in dataset.column_names` once per pass and passes that value into `create_generic_request(row, idx, generation_params_per_row)`, so the planner measures exactly the request the writer will produce. OpenAI processor, `max_requests_per_batch=1_000_000`, `max_bytes_per_batch` patched to 480, 6 rows with columns `{"prompt": ["say 0"…"say 5"], "generation_params": ['{"temperature": 0.9}']*6}`: every row measures 173 bytes and the plan is 3 batches `[PlannedBatch(0,0,2,2,347), PlannedBatch(1,2,4,2,347), PlannedBatch(2,4,6,2,347)]` with file line counts `[2,2,2]`. On the same processor with a 6-row dataset that has no `generation_params` column, planning succeeds at 153 bytes per row and 2 batches `[PlannedBatch(0,0,3,3,461), PlannedBatch(1,3,6,3,461)]` — no `KeyError('generation_params')`.
- **exclusions_or_crossover** — `payload_size_bytes(d)` is exactly `len(json.dumps(d).encode())` — stock `json.dumps` arguments: `ensure_ascii=True`, `", "` / `": "` separators, no `default=` fallback — byte-identical to the serialization `create_batch_file` already performs, so the planner's ruler and the submission-time check cannot diverge. Same single-row OpenAI setup as above but with content `"café"`: `payload_size_bytes(api_request) == 157` (`ensure_ascii=False` gives 153, compact separators give 144).
- **failure_behavior** — A payload containing a non-JSON-serialisable value propagates `TypeError` out of the planner rather than being coerced through a `default=str` fallback or converted to another error type: `payload_size_bytes({"a": {1, 2}})` raises `TypeError` (not `ValueError`, and does not return an int).
- **observability** — `create_api_specific_request_batch` is invoked exactly once per dataset row per planning pass, in index order — no re-measuring of boundary rows when a batch closes, no pre-fetched `max_requests_per_batch`-sized windows, no separate measure-then-log second pass. With that method wrapped in a `unittest.mock.Mock` whose `side_effect` delegates to the real method, OpenAI processor, 6 rows of `{"prompt": "say N"}`, `max_requests_per_batch=6`, `max_bytes_per_batch=400`: after `create_request_files(dataset)`, `spy.call_count == 6` (window re-measurement gives 8, a two-pass split gives 12) while the resulting plan is `[(0,2),(2,4),(4,6)]` in every case.
- *earlier, reversed*: The planner originally sized rows with `len(json.dumps(request.model_dump(), default=str).encode())` on the generic request (base_request_processor.py:271); that ruler was adopted and later reversed once batches it packed were rejected at submission by create_batch_file.

## r2
- **rule** — `plan_batches` walks `sizes` once in index order and appends each request to the current batch if the batch still fits, otherwise closes it and starts a new batch at that request; batches are contiguous, ordered and exhaustive spans (`plan[0].start_idx == 0`, `plan[i].end_idx == plan[i+1].start_idx`, `plan[-1].end_idx == len(sizes)`), rows are not reordered, not bin-packed, and the batch count is not smoothed. `plan_batches([10]*7, BatchLimits(1000, 32))` returns exactly `[PlannedBatch(0,0,3,3,32), PlannedBatch(1,3,6,3,32), PlannedBatch(2,6,7,1,10)]` — sizes `[3,3,1]`, not an even `[3,2,2]` split.
- **scope** — Both limits are inclusive: a batch stays admissible while `payload_bytes(batch) <= max_bytes_per_batch` and `len(batch) <= max_requests_per_batch`, so a batch landing exactly on either limit is kept and no safety headroom is subtracted from either limit. `plan_batches([10]*6, BatchLimits(max_requests_per_batch=3, max_bytes_per_batch=32))` returns exactly 2 batches, `PlannedBatch(0,0,3,3,32)` and `PlannedBatch(1,3,6,3,32)`; the pair `(len(plan), plan[0].num_bytes)` is `(2, 32)`.
- **exclusions_or_crossover** — File-level accounting is `payload_bytes(sizes) == sum(sizes) + len(sizes) - 1` for a non-empty sequence and `0` for an empty one — the `n-1` separators of `"\n".join(...)` with no trailing newline — and every `PlannedBatch.num_bytes` is `payload_bytes` of that batch's row sizes. The per-line trailing-newline accounting used by the request-file writer (`json.dumps(...) + "\n"`) must not be used here. `payload_bytes([]) == 0`, `payload_bytes([10]) == 10`, `payload_bytes([10,10,10]) == 32`; `plan_batches([10]*7, BatchLimits(1000, 32))[0].num_requests == 3` and `plan_batches([10]*7, BatchLimits(1000, 31))[0].num_requests == 2`; `create_batch_file([])` returns `b""` and raises nothing.
- **failure_behavior** — If a single request's own size exceeds `max_bytes_per_batch`, `plan_batches` raises `SingleRequestTooLargeError(row_idx=<index>, size_bytes=<that size>, limit_bytes=<limit>)` — a subclass of `BatchPayloadTooLargeError` exported from the same module, whose `num_requests` attribute is 1 — before returning any plan, instead of emitting the row as a one-request batch, skipping it, or deferring the check to submission. `plan_batches([10, 500, 10], BatchLimits(1000, 32))` raises it with `err.row_idx == 1`, `err.size_bytes == 500`, `err.limit_bytes == 32`, `err.num_requests == 1`, `isinstance(err, BatchPayloadTooLargeError)`, `isinstance(err, ValueError)`. End to end: OpenAI processor with `max_bytes_per_batch` patched to 400 and `Dataset.from_dict({"prompt": ["ok", "x"*600, "ok"]})`, `create_request_files(big)` raises `SingleRequestTooLargeError(row_idx=1, size_bytes=748, limit_bytes=400)` and `glob("requests_*.jsonl")` is empty because nothing is written before planning completes.
- **observability** — The `"auto"` branch of `create_request_files` returns one path per `PlannedBatch` ordered by `PlannedBatch.index` — `[os.path.join(self.working_dir, f"requests_{p.index}.jsonl") for p in plan]`, with `metadata_{index}.json` written alongside — rather than a stale single-element list or a lexicographically sorted glob of the working dir. OpenAI processor, `max_requests_per_batch` patched to 1, generous byte limit, 11-row dataset: `create_request_files(dataset)` returns a list of length 11 whose basenames are exactly, in order, `requests_0.jsonl … requests_10.jsonl`, so `basename(result[1]) == "requests_1.jsonl"` and `basename(result[10]) == "requests_10.jsonl"`.
- *earlier, reversed*: An earlier fix guarded the loop with `max(batch_size, 1)` so an oversized row became a batch of its own and failed later at submission; that was reversed in favour of raising `SingleRequestTooLargeError` at plan time before any file is written.
