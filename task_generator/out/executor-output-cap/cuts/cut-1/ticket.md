# Sandbox stdout/stderr output cap

Sandboxed runs can hand back arbitrarily large stdout/stderr, and we serialize those straight into response records; add a byte budget for the two streams. Build a new module `src/bespokelabs/curator/code_executor/output_cap.py` that holds the whole capping rule and exports: `DEFAULT_MAX_OUTPUT_BYTES: int = 65536`; a frozen `@dataclass` `CappedStream` with fields, in declaration order, `text: str | None`, `truncated: bool`, `original_bytes: int`, `kept_bytes: int`; a frozen `@dataclass` `StreamCapReport` with fields, in declaration order, `stdout: str | None`, `stderr: str | None`, `truncated_streams: list[str]` (neither is a NamedTuple, a tuple, a dict, or a pydantic model); `cap_stream(data: str | bytes | None, max_bytes: int = DEFAULT_MAX_OUTPUT_BYTES) -> CappedStream`, which enforces the budget on `data` and reports the resulting text, whether anything had to be cut, the input's size in bytes and how many bytes it kept; and `cap_execution_streams(stdout: str | bytes | None, stderr: str | bytes | None, max_bytes: int = DEFAULT_MAX_OUTPUT_BYTES) -> StreamCapReport`, which applies it to both streams and names the ones that were cut. In `types.py`, `CodeExecutionBackendConfig` gains `max_output_bytes: int = Field(default=65536, ge=0)` (reachable via `CodeExecutor(backend_params={...})` for every backend name — `_factory.py` already does `CodeExecutionBackendConfig(**backend_params)` and needs no edit), and `CodeExecutionOutput` and `CodeExecutionResult` each gain `truncated_streams: list[str] = []`. In `sandbox_backend.py`, `SandboxCodeExecutionBackend.__init__` stores `self.max_output_bytes: int = config.max_output_bytes`, `execute_request` passes `max_output_bytes=self.max_output_bytes` into its `partial(_execute_in_sandbox, ...)`, and `_execute_in_sandbox(code, code_input, timeout, backend_name, sandbox_kwargs, *, max_output_bytes: int = DEFAULT_MAX_OUTPUT_BYTES)` takes it keyword-only (positional passing must raise `TypeError`) and returns capped streams plus `truncated_streams` on the `CodeExecutionOutput` it builds. `_format_exit_code_error`'s signature and its `"Program exited with status code {status}\n\nError details:\n{stderr}"` message text stay as they are, and `_collect_sandbox_files` / the `files` field are untouched. Tests exercise `_execute_in_sandbox` directly through the existing fake-`bespokelabs.sandbox` monkeypatch seam in `tests/code_executor/test_sandbox_backend.py`; no new dependency.
