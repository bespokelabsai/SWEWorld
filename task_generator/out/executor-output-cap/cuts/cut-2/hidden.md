# Hidden requirements — g2 (executor-output-cap)

## r1
- **rule** — When a stream exceeds the budget, the kept payload is the first (max_bytes * 3) // 4 bytes of the UTF-8 encoding followed by the last max_bytes - (max_bytes * 3) // 4 bytes, with the middle dropped — for max_bytes=64 that is a 48-byte head and a 16-byte tail, so cap_stream('0123456789'*10, 64).text starts with '012345678901234567890123456789012345678901234567' and ends with '4567890123456789'.
- **scope** — The budget is measured on the UTF-8 encoding, and both slices are trimmed to codepoint boundaries before decoding: for the head, try removing 0, 1, 2 then 3 trailing bytes and take the first candidate that decodes; for the tail, try dropping 0, 1, 2 then 3 leading bytes and take the first that decodes; only when no candidate within three bytes decodes (genuinely invalid UTF-8) fall back to the untrimmed slice decoded with errors='replace'. kept_bytes may therefore land below max_bytes, and a clean multi-byte input never produces U+FFFD: cap_stream('€'*10, 20) == CappedStream('€€€€€\n[[curator:elided 12 bytes]]\n€', True, 30, 18) — kept_bytes 18, exactly six '€', no '�'.
- **exclusions_or_crossover** — max_bytes == 0 is the disable sentinel and is exempt from the floor check: it never raises and returns the entire stream with truncated=False and kept_bytes == original_bytes (cap_stream('A'*100000, 0) keeps all 100000 characters). data=None is preserved as text=None, never coerced to '' — cap_stream(None, 64) == CappedStream(None, False, 0, 0) — while data='' or b'' returns text='' with truncated=False and original_bytes=0.
- **failure_behavior** — cap_stream, and therefore cap_execution_streams, raises OutputCapError — a ValueError subclass defined in output_cap.py that carries an attribute max_bytes set to the offending value — whenever max_bytes != 0 and max_bytes < MIN_MAX_OUTPUT_BYTES, a module constant equal to 16. The check runs before the data-is-None check, so cap_stream(None, 8) raises with exc.max_bytes == 8 rather than returning; cap_stream(b'x', 15) / (b'x', 1) / (b'x', -1) raise with matching .max_bytes; cap_stream(b'x', 16) returns CappedStream('x', False, 1, 1).
- **observability** — Head and tail are joined by exactly '\n[[curator:elided {dropped} bytes]]\n' where {dropped} is the decimal original_bytes - kept_bytes (bytes actually thrown away, not original_bytes - max_bytes) with no thousands separator, and the marker sits outside the budget: kept_bytes never counts it, so the returned text is longer than max_bytes by exactly the marker's length. For cap_stream('0123456789'*10, 64): the substring '\n[[curator:elided 36 bytes]]\n' begins at offset 48, len(text) == 93 (64 + 29), kept_bytes == 64, original_bytes == 100.
- *earlier, reversed*: The first cut reserved room for the notice inside the budget so that len(text.encode()) <= max_bytes always held, and clamped tiny caps up to the floor instead of raising; both were reversed — the marker was moved outside the budget so the kept payload is exactly the requested size, and a sub-floor cap became a hard OutputCapError.

## r2
- **rule** — On the non-zero-exit path, the stderr embedded in the exit-code error message is the capped stderr text, not result.stderr, so output.error == 'Program exited with status code {code}\n\nError details:\n' + output.stderr exactly. Only the stderr portion is subject to the budget: the fixed prefix is not counted against it, the assembled message is not re-capped as a whole, and the details are not replaced by a 'see stderr field' note. With a fake sandbox returning exit_code=1, stderr='E'*80, stdout='' and max_output_bytes=64, len(output.error) == 143.
- **scope** — The cap is applied inside _execute_in_sandbox at every CodeExecutionOutput it constructs — the success path, the exit_code == 124 timeout path, the non-zero-exit path, and the except-Exception path whose streams are salvaged via getattr(result, 'stdout'/'stderr', None) — rather than once at the point the streams are first read into locals, and not in a post-processing wrapper in execute_request or base_backend. A fake sandbox returning exit_code=0, stdout='A'*300 whose __exit__ raises RuntimeError('boom') still yields message == 'error', error == 'boom', len(output.stdout) == 94 ending in 'A'*16, and stderr == ''; a fake with exit_code=124, stdout='A'*300 yields message == 'timeout', error == 'Execution timed out after 7s' and len(output.stdout) == 94.
- **observability** — truncated_streams contains exactly the names of the streams that were actually truncated — the bare strings 'stdout' and 'stderr', no prefix or field path — sorted alphabetically, so a run with both truncated reports ['stderr', 'stdout'] rather than argument/field/read order, cap_execution_streams('A'*300, None, 64).truncated_streams == ['stdout'], and cap_execution_streams('a', 'b', 64).truncated_streams == []. A stream that is None, empty, or under budget contributes nothing, and the list appears unchanged under exec_output after CodeExecutionResponse(...).model_dump().
- *earlier, reversed*: The branch first capped once at the read site (stdout = result.stdout / stderr = result.stderr) and left the except-Exception path untouched as best-effort passthrough; that was reversed after a run whose Sandbox.__exit__ raised shipped an uncapped multi-megabyte stdout, and the same review found error still carrying the full stderr.
