# Sandbox stdout/stderr output cap

Sandboxed runs return whatever the program wrote, so a runaway `print` loop ships megabytes of stdout through `CodeExecutionOutput` into the response file. Add a configurable byte budget for the stdout/stderr that `SandboxCodeExecutionBackend` returns, with the capping rule itself in a new pure module `src/bespokelabs/curator/code_executor/output_cap.py` (a pure function of its arguments — no clock, randomness or I/O) exporting: `DEFAULT_MAX_OUTPUT_BYTES: int = 65536`; a real `@dataclass(frozen=True)` (not a pydantic model, `NamedTuple`, dict or tuple) `CappedStream` with fields, in this declaration order, `text: str | None`, `truncated: bool`, `original_bytes: int`, `kept_bytes: int`; a frozen `StreamCapReport` with fields, in this order, `stdout: str | None`, `stderr: str | None`, `truncated_streams: list[str]`; and two functions `cap_stream(data: str | bytes | None, max_bytes: int = DEFAULT_MAX_OUTPUT_BYTES) -> CappedStream` and `cap_execution_streams(stdout: str | bytes | None, stderr: str | bytes | None, max_bytes: int = DEFAULT_MAX_OUTPUT_BYTES) -> StreamCapReport`. `original_bytes` is the UTF-8 byte length of the input (`0` for `None`), `kept_bytes` is the byte count of the input's surviving portion, `truncated` says whether the stream was shortened, and `text` is `None` only when `data is None` (a null stream is never coerced to `""`). In `types.py`, `CodeExecutionBackendConfig` gains `max_output_bytes: int = Field(default=65536, ge=0)` — `_factory.py:31` already does `CodeExecutionBackendConfig(**backend_params)`, so it is reachable as `CodeExecutor(backend_params={"max_output_bytes": ...})` for every backend name with no factory edit, and a negative value must be rejected at construction with pydantic's `ValidationError`; `CodeExecutionResult` and `CodeExecutionOutput` each gain a non-Optional `truncated_streams: list[str] = []` naming which of `"stdout"`/`"stderr"` were shortened on that run (a stream that is `None`, empty or under budget contributes nothing), and the field must survive `CodeExecutionResponse(...).model_dump()`. In `code_execution_backend/sandbox_backend.py`, `__init__` sets `self.max_output_bytes: int`, `execute_request` passes `max_output_bytes=self.max_output_bytes` into the existing `partial(_execute_in_sandbox, ...)`, and the module-level function becomes `_execute_in_sandbox(code, code_input, timeout, backend_name, sandbox_kwargs, *, max_output_bytes: int = DEFAULT_MAX_OUTPUT_BYTES)` — keyword-only after a bare `*`, so a positional sixth argument raises `TypeError`. Capping applies at all four `CodeExecutionOutput` construction sites: success, the `exit_code == 124` timeout, the non-zero exit, and the `except Exception` path whose streams come from `getattr(result, "stdout", None)` and may be `None`. The existing error-message and file-collection helpers keep their current signatures and message text, and `files` is not capped; nothing in `_factory.py`, `code_executor.py` or `db.py` changes. Python 3.10, pydantic >=2.9.2, no new dependency; the whole thing must be testable directly and through the fake `bespokelabs.sandbox` module seam already used by `tests/code_executor/test_sandbox_backend.py`.
