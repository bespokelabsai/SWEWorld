# Hidden requirements — g13 (raft-document-set)

## r1
- **rule** — A new module-level mutable `@dataclass class RaftDrawStats` with exactly two fields in this order, `document_sets: int = 0` and `with_oracle: int = 0`, plus one method `oracle_rate(self) -> float` returning `self.with_oracle / self.document_sets` (and `0.0` when `document_sets == 0`). `_RaftAnswer.__init__` sets `self.stats = RaftDrawStats()` after `self.formatter`. Nothing in the block reads `stats`; it exists so a finished run can be asked what oracle rate it actually realised. Checkable: `[f.name for f in dataclasses.fields(RaftDrawStats)] == ["document_sets", "with_oracle"]`, `RaftDrawStats() == RaftDrawStats(document_sets=0, with_oracle=0)`, `RaftDrawStats().oracle_rate() == 0.0`.
- **scope** — The counters follow document-set builds, not emitted rows: exactly one increment of `document_sets` per build that actually runs, plus one of `with_oracle` when that build's coin said the oracle is present. A memoised replay increments nothing. On the five-chunk fixture (`["alpha","bravo","charlie","delta","echo"]`, `distractors=2`, `p=0.5`, `sampler=lambda pop, k: list(pop)[:k]`, `rng=random.Random(7)`) parsed with `(0,"Who?")`, `(0,"What?")`, `(2,"Who?")`, `(0,"Who?")` — four `parse` calls, one of them a repeat — `gen.stats == RaftDrawStats(document_sets=3, with_oracle=2)` and `gen.stats.oracle_rate() == 0.6666666666666666`. Counting `parse` calls instead gives `RaftDrawStats(document_sets=4, with_oracle=3)`.
- **exclusions_or_crossover** — The unit the oracle coin is drawn per is the question, not the chunk: the document-set builder takes a third positional parameter `question: Question` which participates in the memoisation key and in nothing else, and `parse` passes `(chunk_id, oracle_document, question)` positionally in that order. A repeat of the same `(chunk_id, question)` replays the memoised `DocumentSet` and consumes no rng; two different questions on one chunk get independent coins and can differ in `oracle_present`. On the fixture above, a spy rng records exactly three `"random"` calls across the four `parse` calls, and `rows[3] == rows[0]` while `rows[1]` (`oracle_present=False`) differs from `rows[0]` (`oracle_present=True`) on the same chunk.
- **observability** — The memoisation bound is `functools.lru_cache(maxsize=512)`: on any constructed `_RaftAnswer`, `gen._get_document_set.cache_info().maxsize == 512`, and on the four-call fixture above `cache_info() == CacheInfo(hits=1, misses=3, maxsize=512, currsize=3)`.
- *earlier, reversed*: The counters first lived in `parse` and incremented once per emitted row; they were moved into the builder after a repeated question on one chunk was counted twice and the reported rate drifted above the realised one.

## r2
- **rule** — A new module-level `InsufficientDistractorsError(ValueError)` raised by the document-set builder when the corpus cannot supply the distractors. It is constructed `InsufficientDistractorsError(chunk_id=chunk_id, requested=requested, available=available)`, carries exactly those three attributes, and `str(exc)` is exactly `f"chunk {chunk_id}: requested {requested} distractors, only {available} available"`. On chunks `["a","b","c","d"]` with `distractors=3` and `chunk_id=2`: `isinstance(exc, ValueError)` is `True`, `(exc.chunk_id, exc.requested, exc.available) == (2, 4, 3)` and `str(exc) == "chunk 2: requested 4 distractors, only 3 available"`.
- **scope** — The check is the builder's first statement and consumes no randomness: `available = len(self.chunks) - 1`, `requested = self.distractors + 1` — the oracle-absent worst case, regardless of how the coin would land — and it raises when `available < requested`. So a corpus with `len(chunks) - 1 == distractors` fails on every chunk deterministically instead of only on the chunks that happen to draw the absent branch: with `p=1.0` (where the present branch would need only 3 of the 3 available), `parse({"chunk_id": 2, "question": "Q"}, "resp")` still raises, and a spy rng records `rng.calls == []`.
- **failure_behavior** — `_RaftAnswer.__init__` validates its two numeric knobs as its first statements, before `super().__init__(*args, **kwargs)` runs, `p` before `distractors`, raising plain `ValueError` (never `InsufficientDistractorsError`, which is reserved for the corpus-size failure): `p` outside the closed interval gives `"p must be in [0.0, 1.0], got 1.5"` / `"p must be in [0.0, 1.0], got -0.1"`, and `distractors < 1` gives `"distractors must be >= 1, got 0"` / `"distractors must be >= 1, got -2"`. `p=1.5, distractors=0` together give the `p` message. `p=0.0`, `p=1.0` and `distractors=1` all construct. Placement is visible through the base class: `_RaftAnswer(chunks=..., model_name="gpt-4o-mini", backend="nope")` raises `ValueError("Unknown backend: nope")`, while adding `p=1.5` to that same call raises `"p must be in [0.0, 1.0], got 1.5"`. `Raft` itself does not re-check, so `Raft(model="m", p=1.5)` constructs and fails only when `__call__` builds the answer generator.
- **exclusions_or_crossover** — In `Raft.__call__`'s list branch only, entries whose `str.strip()` is empty are dropped before chunk ids are assigned and the survivors are renumbered contiguously from `0`; surviving text is stored verbatim, surrounding whitespace kept. The `str` branch is untouched. With kwarg-recording stubs, `Raft(model="m", ...)(["alpha", "", "  ", "\n", " bravo "])` gives `len(StubA.kw["chunks"]) == 2`, `StubA.kw["chunks"]["content"] == ["alpha", " bravo "]`, `StubA.kw["chunks"]["chunk_id"] == [0, 1]`; `(["", "   ", "\t\n"])` gives `len(...) == 0` with `column_names == []` and raises nothing here; `("abcdefghij")` still gives `content == ["abcdefghij"]`, `chunk_id == [0]`.
- *earlier, reversed*: The availability check was first done lazily per branch — `distractors` when the coin said present, `distractors + 1` when absent — and was reverted to the up-front worst case after the same corpus passed or failed depending on the seed.
