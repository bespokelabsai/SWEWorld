# Hidden requirements — g3 (retry-backoff-policy)

## r1
- **rule** — `decide` sets `attempt_index = attempts_made + 1` and then prices the failure in attempts, with per-class costs that are not all 1: `TRANSIENT` costs 1, `CONTRACT` costs 2, and `THROTTLE` costs 0 for as long as the request still holds a throttle waiver. The waiver budget is a third piece of per-request state that `decide` takes and returns: `retry_policy` exports `DEFAULT_THROTTLE_WAIVERS: int = 6`, `APIRequest` gains `throttle_waivers_left: int = DEFAULT_THROTTLE_WAIVERS`, `decide`'s full keyword signature is `decide(exc, *, attempts_made: int, attempts_left: int, throttle_waivers_left: int)`, and `RetryVerdict` has an eighth field `throttle_waivers_after: int` sitting between `attempts_left_after` and `tracker_field` (field order: `should_retry`, `failure_class`, `attempt_index`, `delay_seconds`, `attempts_left_after`, `throttle_waivers_after`, `tracker_field`, `reason_code`). On a `THROTTLE` failure with `throttle_waivers_left > 0` the cost is 0 and `throttle_waivers_after = throttle_waivers_left - 1`; once the waivers are spent the cost is 1 and `throttle_waivers_after` stays 0. Every other class leaves `throttle_waivers_after == throttle_waivers_left`.
- **scope** — The waiver counter is per-request state carried on `APIRequest` and seeded at construction from `DEFAULT_THROTTLE_WAIVERS`; it is not a config knob, not a field on `OnlineStatusTracker`, and not shared across requests. `decide` stays pure — it reads the three budget numbers handed to it and returns the new ones on the verdict; the base-class `except` block is what assigns `request.attempts_made = verdict.attempt_index`, `request.attempts_left = verdict.attempts_left_after` and `request.throttle_waivers_left = verdict.throttle_waivers_after`.
- **exclusions_or_crossover** — `TERMINAL` is never retried and discards the rest of the budget: `should_retry=False`, `attempts_left_after=0` even when `attempts_left` was 7, `throttle_waivers_after` untouched, outcome `"abort"`. Conversely a zero-cost `THROTTLE` at `attempts_left == 0` satisfies `0 - 0 >= 0` and is still retried (`"throttle:retry"`, `attempts_left_after == 0`) — a spent budget only stops a throttle failure once the waivers are also gone.
- **failure_behavior** — Exhaustion is decided after the cost is subtracted, not before: if `attempts_left - cost < 0` the verdict is `should_retry=False`, `attempts_left_after=0` (clamped, never negative), `delay_seconds=0.0`, outcome `"exhausted"`. So a `CONTRACT` failure at `attempts_left == 1` is exhausted rather than being granted a last try that leaves the budget at `-1`.
- **observability** — With a jitter source returning 0.25: `decide(Exception("rate limit"), attempts_made=0, attempts_left=3, throttle_waivers_left=6)` yields `(should_retry, attempt_index, attempts_left_after, throttle_waivers_after) == (True, 1, 3, 5)`; `decide(Exception("rate limit"), attempts_made=9, attempts_left=0, throttle_waivers_left=3)` yields `should_retry is True`, `attempts_left_after == 0`, `throttle_waivers_after == 2`, `reason_code == "throttle:retry"`, while the same call with `throttle_waivers_left=0` yields `reason_code == "throttle:exhausted"`; `decide(ValueError("bad"), attempts_made=0, attempts_left=3, throttle_waivers_left=6)` gives `attempts_left_after == 1`, and at `attempts_left=1` gives `(False, 0, "contract:exhausted")`; `decide(Exception("invalid api key"), attempts_made=2, attempts_left=7, throttle_waivers_left=6)` gives `(False, FailureClass.TERMINAL, 3, 0.0, 0, 6, "num_api_errors", "terminal:abort")`. `DEFAULT_THROTTLE_WAIVERS == 6` and a freshly built `APIRequest` reports `throttle_waivers_left == 6`, `attempts_made == 0`, `failure_log == []`.
- *earlier, reversed*: An earlier build made throttle failures free with no cap at all (rate limits simply never decremented `attempts_left`), which the outage postmortem reversed in favour of a bounded six-waiver allowance per request.

## r2
- **rule** — `delay_for(failure_class, attempt_index)` reads `(base, factor, cap)` from a per-class schedule — `THROTTLE (8.0, 2.0, 60.0)`, `TRANSIENT (0.5, 3.0, 20.0)`, `CONTRACT (0.0, 1.0, 0.0)`, `TERMINAL (0.0, 1.0, 0.0)` — computes `raw = min(cap, base * factor ** (attempt_index - 1))` so the cap is applied *before* jitter and the result can never exceed `cap`, returns `0.0` at once when `raw <= 0`, and otherwise returns `round(raw * (0.5 + 0.5 * j), 3)`, where `j` is the value from the injected jitter source clamped into `[0.0, 1.0]` by `min(1.0, max(0.0, j))`. This is half-jitter, not full jitter: the delay is always in `[raw/2, raw]`. None of these numbers come from `config.seconds_to_pause_on_rate_limit`, which becomes dead configuration that the policy never reads.
- **scope** — The jitter source is consumed exactly once per positive delay and not at all otherwise: `RetryPolicy.__init__` calls neither callable, `delay_for` invokes `jitter()` only on the `raw > 0` path, and `decide` calls `delay_for` only when it is about to return `should_retry=True` — an aborted or exhausted verdict sets `delay_seconds = 0.0` without consulting the schedule. `clock` is likewise untouched by `delay_for` and `decide`; it is called once, and only for `THROTTLE` verdicts, inside `apply_to_tracker`.
- **exclusions_or_crossover** — `CONTRACT` is retried but never waits: a `CONTRACT` verdict carries `delay_seconds == 0.0` and consumes no jitter draw, exactly as `TERMINAL` does, so re-asking after a schema violation is immediate while a `TRANSIENT` failure at the same attempt index waits. `TRANSIENT` also uses factor 3.0 rather than the 2.0 that `THROTTLE` uses.
- **failure_behavior** — `delay_for` raises `ValueError` when `attempt_index < 1` (attempt indices are 1-based); it does not silently treat 0 or a negative index as the first attempt, and it does not draw jitter before validating.
- **observability** — With a jitter source returning 0.25 (multiplier 0.625): `delay_for(THROTTLE, 1) == 5.0`, `(…, 2) == 10.0`, `(…, 3) == 20.0`, `(…, 4) == 37.5` and `(…, 9) == 37.5`; `delay_for(TRANSIENT, 1) == 0.312`, `(…, 2) == 0.938`, `(…, 3) == 2.812`, `(…, 4) == 8.438`, `(…, 5) == 12.5`, `(…, 20) == 12.5`; `delay_for(CONTRACT, 1) == 0.0` and `delay_for(TERMINAL, 3) == 0.0`. With jitter 0.0 `delay_for(THROTTLE, 1) == 4.0`; with 1.0, `8.0`; with the out-of-range 2.5, `8.0`; with `-1.0`, `4.0`. `delay_for(THROTTLE, 0)` raises `ValueError`. Counting calls into the jitter source: three `decide` calls on `ValueError("bad")` with a healthy budget leave the count at 0, one `decide` on `Exception("rate limit")` raises it by exactly 1, an exhausted `TimeoutError` decision leaves it unchanged, and constructing a `RetryPolicy` leaves it at 0.
- *earlier, reversed*: The first cut reused the existing `seconds_to_pause_on_rate_limit` (10.0) as a single base for every class with plain doubling and full jitter; it was reversed after a run's tail sat in multi-minute uncapped sleeps and the config knob was left in place purely for backwards compatibility.
