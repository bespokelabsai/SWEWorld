# Hidden requirements — g10 (token-capacity-budget)

## r1
- **rule** — The tracker has two distinct release operations, not one. `refund_capacity(self, blocked: _TokenUsage) -> None` credits the *entire* blocked estimate back to the token axes (each axis capped above at its per-minute limit) **and** gives back exactly `1.0` of `available_request_capacity` (capped above at `max_requests_per_minute`), incrementing a counter field `num_capacity_refunds`. The settlement `free_capacity(used, blocked)` credits only the `blocked - used` delta and leaves `available_request_capacity` completely alone, incrementing a separate counter field `num_capacity_settlements`. Both counters are tracker fields defaulting to `0`. `BaseOnlineRequestProcessor` exposes `_refund_capacity(self, status_tracker, blocked_capacity) -> None`, which does nothing but delegate to `status_tracker.refund_capacity(blocked_capacity)`.
- **scope** — Every exit through `except Exception` in `handle_single_request_with_retries` releases via `_refund_capacity(status_tracker, blocked_capacity)` — with the full blocked estimate, ignoring `generic_response.token_usage` even when the failed response carried one and even though the `except` block already builds that `used_tokens` value for `update_cost_projection`. Only the success/`else` path uses `_free_capacity(status_tracker, used_tokens, blocked_capacity)`.
- **exclusions_or_crossover** — The requeued failure (`attempts_left > 0`, request pushed back on the retry queue) and the permanently-failed attempt (`attempts_left == 0`) release identically: both get the full refund, including the `1.0` request slot. Neither is downgraded to a settlement, and the requeue path is not skipped on the theory that the retry will reserve again.
- **observability** — Tracker at `max_requests_per_minute=60`, `max_tokens_per_minute=10_000`, frozen clock, after `blocked = proc._reserve_capacity(tracker, [])` with estimate `_TokenUsage(input=700, output=300)` (→ `59.0` / `9000.0`): a failing attempt (`finish_reason="length"`, reported `token_usage=_TokenUsage(input=700, output=300)`, `attempts_left=0`) leaves `available_token_capacity == 10000.0`, `available_request_capacity == 60.0`, `num_capacity_refunds == 1`, `num_capacity_settlements == 0`; the same run with `attempts_left=1` gives the identical numbers. A successful attempt (`finish_reason="stop"`, usage `input=700, output=100`) leaves `available_token_capacity == 9200.0`, `available_request_capacity == 59.0`, `num_capacity_settlements == 1`, `num_capacity_refunds == 0`. Refunding twice caps at `60.0` / `10000.0`.
- *earlier, reversed*: An earlier patch released the failure path symmetrically with the success path — `_free_capacity(status_tracker, used_tokens, blocked_capacity)` with the reported usage when the response carried one — and was reverted after a run against a systematically failing model still drained the token bucket over ten retries; the team settled on refunding the failed attempt whole.

## r2
- **rule** — Token capacity is allowed to go into debt when an estimate was too low, but never below `-CAPACITY_DEBT_FLOOR_FRACTION * limit` with `CAPACITY_DEBT_FLOOR_FRACTION: float = 0.25` defined in `capacity_budget.py`. The floor is `-limit * 0.25` as a `float` for the `combined` axis and `math.ceil(-limit * 0.25)` — an `int` — for each `seperate` axis.
- **scope** — The clamp is applied at the end of each token-capacity mutation that can drive an axis negative: `consume_capacity`, `free_capacity` and the refund path. It is not applied to the time-based refill in `update_capacity`, which only ever raises an axis toward its cap.
- **exclusions_or_crossover** — `available_request_capacity` is outside the floor entirely: it is only decremented after a successful `has_capacity`, so it stays `>= 0.0` and is never clamped or counted. A negative token result that stays above the floor is preserved exactly as computed and is not counted as a clamp.
- **failure_behavior** — An axis whose limit/capacity is `None` (unlimited) has no floor: it is skipped, stays `None`, and cannot contribute a clamp.
- **observability** — A tracker field `num_capacity_debt_clamps` (default `0`) increments by exactly **one** per call in which at least one axis was clamped — one, not one per axis. With `max_requests_per_minute=60`, `max_tokens_per_minute=1_000`, frozen clock: `consume_capacity(_TokenUsage(input=700, output=100))` → `200.0`, then `free_capacity(used=_TokenUsage(input=1000, output=500), blocked=_TokenUsage(input=700, output=100))` → `available_token_capacity == -250.0`, `num_capacity_debt_clamps == 1`, `available_request_capacity == 59.0`. A settlement that lands above the floor does not count: `consume_capacity(_TokenUsage(input=700, output=100))` then `free_capacity(used=_TokenUsage(input=700, output=200), blocked=_TokenUsage(input=700, output=100))` → `100.0` with `num_capacity_debt_clamps == 0`. Under `seperate` with `max_tokens_per_minute=_TokenUsage(input=1_000, output=500)`, over-settling both axes yields `_TokenUsage(input=-250, output=-125, total=-375)` and `num_capacity_debt_clamps == 1`.
- *earlier, reversed*: Debt was first clamped at `0.0` (an underestimate simply forgotten), then briefly left unbounded to match the old `free_capacity` docstring's 'This can be a negative number incase of under estimation', before the team settled on the −25 % floor plus a clamp counter.
