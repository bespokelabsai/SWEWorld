# Hidden requirements — g10 (token-capacity-budget)

## r1
- **rule** — Token capacity may go negative when a settlement discovers an under-estimate, but each axis is floored at `-CAPACITY_DEBT_FLOOR_FRACTION * limit` with `CAPACITY_DEBT_FLOOR_FRACTION: float = 0.25` exported from the capacity-budget module. The floor is `-limit * 0.25` as a `float` for the `combined` axis and `math.ceil(-limit * 0.25)` (an `int`) for each `seperate` axis, and it is applied at the end of `consume_capacity` and of both release operations. Worked case: a tracker with `max_tokens_per_minute=1_000`, after `consume_capacity(_TokenUsage(input=700, output=100))` and then settling `used=_TokenUsage(input=1000, output=500)` against `blocked=_TokenUsage(input=700, output=100)`, ends at `available_token_capacity == -250.0` (not `-700.0`, not `0.0`).
- **scope** — The floor is computed from the tracker's *effective* per-minute limit after `__post_init__` normalisation, so a tracker constructed with `max_tokens_per_minute=0` (defaulted to 100_000) floors at `-25000.0`, and under `seperate` each axis floors against its own limit: with `_TokenUsage(input=1_000, output=500)` an over-settled tracker lands on `_TokenUsage(input=-250, output=-125, total=-375)`. An axis whose limit and capacity are `None` has no floor and stays `None`. `available_request_capacity` is never floored because it is only decremented after a successful `has_capacity`.
- **exclusions_or_crossover** — The upper cap is not a clamp for counting purposes: the refill in `update_capacity` capping an axis at its limit, and a release capping an axis at its limit, leave the clamp counter untouched. Only the lower debt floor counts — a settlement whose result stays above the floor (e.g. `available_token_capacity == 100.0` on a 1_000-token tracker) leaves the counter at `0`.
- **observability** — A tracker field `num_capacity_debt_clamps: int = 0` increments by exactly one per call that clamped at least one axis — one increment per call, not per axis, so the `seperate` case above yields `num_capacity_debt_clamps == 1` even though both axes hit their floors.
- *earlier, reversed*: The team first clamped debt at 0.0 (capacity is never negative, an under-estimate is forgotten), then reversed it because forgiving the overshoot let a systematically under-estimating model exceed the provider's per-minute budget every window; they settled on a bounded -25% carry-over instead.

## r2
- **rule** — Releasing a reservation is two distinct tracker operations, not one. `free_capacity(used, blocked)` is a *settlement*: the token axes gain `blocked - used` and `available_request_capacity` is left exactly as `consume_capacity` left it. A second method `refund_capacity(blocked: _TokenUsage) -> None` is a *refund*: the token axes gain the whole `blocked` estimate back (capped above at the limit) and `available_request_capacity` gains exactly `1.0`, capped above at `max_requests_per_minute`. The processor's failure release is `_refund_capacity(self, status_tracker, blocked_capacity)`, which delegates to `status_tracker.refund_capacity(blocked_capacity)`.
- **scope** — Every terminal path through the `except Exception` branch of `handle_single_request_with_retries` calls the refund immediately before its `return` — both the requeued case (`attempts_left > 0`) and the exhausted case (`attempts_left == 0`). The success `else` path keeps the settlement at its current position. On a tracker with `max_requests_per_minute=60`, `max_tokens_per_minute=10_000` and a reservation of `_TokenUsage(input=700, output=300)`, either failure path ends at `available_request_capacity == 60.0` and `available_token_capacity == 10000.0`, while the success path with reported usage `_TokenUsage(input=700, output=100)` ends at `59.0` / `9200.0`.
- **exclusions_or_crossover** — The failure refund uses the full blocked estimate and ignores `generic_response.token_usage` even when the failed response carried one — e.g. a response with `finish_reason="length"` (in `config.invalid_finish_reasons`) reporting `_TokenUsage(input=900, output=800)` against a blocked estimate of `_TokenUsage(input=900, output=100)` returns the estimate, not the reported spend.
- **observability** — Two tracker counters, `num_capacity_settlements: int = 0` and `num_capacity_refunds: int = 0`, each incremented by exactly one by its own operation and by neither the other's — a failed attempt gives `num_capacity_refunds == 1`, `num_capacity_settlements == 0`, and a successful one the reverse. Both counters still increment when the affected capacity is `None` and the operation is a no-op on every axis.
- *earlier, reversed*: An earlier revision charged the failure path symmetrically with the success path — `_free_capacity(status_tracker, used_tokens, blocked_capacity)` using the usage the `except` block already builds — and returned the request slot on both kinds of release; it was reversed because a retry storm against a systematically failing model drained the bucket faster than the refill could recover it.
