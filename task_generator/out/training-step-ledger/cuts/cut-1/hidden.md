# Hidden requirements — g11 (training-step-ledger)

## r1
- **rule** — The accumulation window is counted over the whole run and is never reset at an epoch boundary, so a window may span epochs: total_steps = ceil(total_batches / gradient_accumulation_steps), step_of_batch(b) = ceil(b / gas), is_step_boundary(b) is true when b % gas == 0 or b == total_batches, and trailing_window_batches = total_batches - (total_steps - 1) * gas (a short final window still counts as one whole optimizer step). That final short window is stepped inside the loop like any other boundary — there is no post-loop flush and no mode-dependent guard around it.
- **scope** — plan_steps / plan_steps_for_config and the rebuilt TinkerTrainer.train loop, including what is handed to FinetuneStatusTracker (constructed with total_steps=plan.total_steps) and what lands in TrainingResult.total_steps / total_batches / step_plan.
- **exclusions_or_crossover** — FireworksTrainer must not use this batch arithmetic at all: it gets its own plan from plan_packed_steps(num_examples, *, epochs, dataset_signature=""), which models Fireworks' server-side token packing as one packed step per epoch — step_unit=STEP_UNIT_PACKED="packed_epoch_step", batch_size=num_examples, gradient_accumulation_steps=1, batches_per_epoch=1, total_batches=epochs, total_steps=epochs, trailing_window_batches=1. Both FireworksTrainer.train and _mock_train report total_steps=plan.total_steps and step_plan=plan instead of the hard-coded total_steps=0, and each metadata dict gains exactly one new key, "step_unit", with value "packed_epoch_step".
- **failure_behavior** — A dataset with no examples is a configuration error, not a zero-step success: plan_steps(0, ...) and plan_packed_steps(0, epochs=...) raise StepLedgerError rather than returning a StepPlan of zeros.
- **observability** — For plan_steps(10, batch_size=3, epochs=2, gradient_accumulation_steps=3): (batches_per_epoch, total_batches, total_steps, trailing_window_batches) == (4, 8, 3, 2); [is_step_boundary(b) for b in 1..8] == [False, False, True, False, False, True, False, True]; [step_of_batch(b)] == [1,1,1,2,2,2,3,3]. plan_steps(10, batch_size=3, epochs=2, gradient_accumulation_steps=4).total_steps == 2 with trailing_window_batches == 4. In train() with a recorder monkeypatched over tinker_trainer_module.FinetuneStatusTracker, that config produces exactly 8 TrainingStats pushes — one per batch, pushed after that batch's optional optimizer step — with [(s.current_batch, s.current_step)] == [(1,0),(2,0),(3,1),(4,1),(5,1),(6,2),(7,2),(8,3)] (current_step counts optimizer steps completed so far, so it stays flat inside a window), {s.total_steps} == {3}, {s.total_batches} == {8}, and the tracker constructed with total_steps=3; a wrapped _training_step records should_optim_step == [False, False, True, False, False, True, False, True], the last True on batch 8.
- *earlier, reversed*: The first cut reset the accumulation window at each epoch boundary (total_steps = ceil(batches_per_epoch / gas) * epochs); it was reversed after it made the last window of every epoch short and made warmup and checkpoint intervals mean different things in different epochs.

## r2
- **rule** — A checkpoint's positional identity is the global batch count, and resume continues from it. save_checkpoint records batches_completed (batches finished across all epochs at that instant) as the only positional fact a resume uses, and records epoch as the epoch that batch ordinal belongs to — plan.epoch_of_batch(batches_completed) — not the loop's epoch variable and not the epoch whose end triggered the write, so a checkpoint carrying the "epoch" reason for the end of epoch 1 records epoch == 2 when the window that carried epoch 1's last batch closed inside epoch 2. plan_resume(plan, checkpoint) then restarts at the batch after the checkpoint: start_batch_ordinal = checkpoint.batches_completed (0-based), start_epoch = batches_completed // plan.batches_per_epoch + 1, start_batch_in_epoch = batches_completed % plan.batches_per_epoch, completed_steps = checkpoint.step, remaining_batches = plan.total_batches - batches_completed. Step numbering continues from completed_steps; the run is neither rewound to the start of the checkpoint's epoch nor restarted at zero.
- **scope** — load_checkpoint stores the whole CheckpointInfo on self._resume_from; the next train() builds the plan for the configured run, calls plan_resume, and skips straight to start_batch_ordinal. self._resume_from is cleared at the start of train(), so a second train() with no fresh load_checkpoint starts from batch 1. Raising epochs alone is a legal resume: the plan grows, total_steps grows, and the remaining batches continue on the new schedule.
- **exclusions_or_crossover** — Only epochs may differ between the checkpoint's run and the configured run — a changed batch_size, gradient_accumulation_steps or dataset is refused, not adapted to. A checkpoint at the very end of its run is refused too rather than treated as a finished no-op resume that returns immediately. Pre-ledger checkpoints (batch_size=0, gradient_accumulation_steps=0, dataset_signature="") fail all three shape comparisons at once.
- **failure_behavior** — Refusal is an exception, not a warning and not a silent restart: ResumePlanMismatch, a subclass of StepLedgerError (hence of ValueError), constructed as ResumePlanMismatch(checkpoint_name, mismatched_fields, expected, found) and exposing .checkpoint_name (str), .mismatched_fields (tuple of the differing names, sorted alphabetically), .expected (dict) and .found (dict). Validation runs in three stages and stops at the first that fails: (1) shape — batch_size, dataset_signature, gradient_accumulation_steps against the plan; (2) exhaustion — checkpoint.batches_completed >= plan.total_batches gives mismatched_fields == ("epochs",); (3) consistency — checkpoint.step != plan.step_of_batch(checkpoint.batches_completed) gives ("step",). The exception propagates out of train().
- **observability** — With plan = plan_steps(10, batch_size=3, epochs=2, gradient_accumulation_steps=3, dataset_signature="ds1-10-5d661fe8c9a2d002") and ck = CheckpointInfo(name="checkpoint-s000002", path=..., step=2, epoch=2, loss=2.3, batch_size=3, gradient_accumulation_steps=3, batches_completed=6, dataset_signature="ds1-10-5d661fe8c9a2d002", reasons=("interval", "epoch")): plan_resume(plan, ck) == ResumePlan("checkpoint-s000002", 6, 2, 2, 2, 2). Against a plan built with batch_size=5 and a different dataset, exc.value.mismatched_fields == ("batch_size", "dataset_signature"); against CheckpointInfo(name="old", path="p", step=4, epoch=2, loss=1.0) it is ("batch_size", "dataset_signature", "gradient_accumulation_steps"); with batches_completed=8 on that plan it is ("epochs",); with the same plan at epochs=3 and batches_completed=8, plan_resume(...).start_epoch == 3 and .remaining_batches == 4; with ck.step forced to 1 it is ("step",). End to end on the 10-example run at batch_size=3, epochs=2, gas=3: the checkpoints record [(step, epoch, batches_completed)] == [(2, 2, 6), (3, 2, 8)]; trainer.load_checkpoint(that first checkpoint) then train(data) yields total_steps == 3, total_batches == 8, samples_processed == 4 and checkpoints named ["checkpoint-s000003"], while train(data[:6]) raises ResumePlanMismatch with mismatched_fields == ("dataset_signature",) and checkpoint_name == "checkpoint-s000002".
- *earlier, reversed*: Resume originally rewound to the start of the checkpoint's epoch and logged a logger.warning when the recorded shape disagreed, matching how every other failure in tinker_trainer.py is handled; it was reversed after a halved batch_size produced a run that replayed examples with no visible error.
