## What happened

The agent ran a genuinely disciplined search: it read the ticket, pulled the two relevant source files, hit BookStack search (near-miss — the terms never matched page titles), then IMAP mail search (found both real mail threads), then Mattermost full-text search across ~15 terms and several rounds of `grep -n -i` over whole pre-dumped channels, and finally wrote a script to fetch all 114 wiki pages with their comments per the ticket's own hint that comments aren't indexed by BookStack search. On paper this is close to a complete strategy. Two things broke it.

**The fatal one: a premature "this doesn't exist" verdict.** At transcript line 1170, having just read the full "sample serialized plan" mail thread (messages 70-76, which specifies `plan_format_version` as `plan_document`'s first-written key), the agent calls it "likely a different/nonexistent feature (distractor)". At line 1939 — after also reading the mail thread about a `plan_id` sidecar gated to the auto branch, and several chat fragments naming `PLAN_FILE_NAME`, the fingerprint recipe, and the envelope shape — it doubles down: "Other threads (plan.json writer, sidecar, plan panel) concern a serialization subsystem that doesn't exist in the repo." It never revisits this. The shipped `batch_payload_planner.py` (written in three heredoc chunks, lines 2997–3266) contains `BatchLimits`, `PlannedBatch`, the three error classes, and `plan_batches` — and nothing else. `PLAN_FILE_NAME`, `plan_fingerprint`, and `plan_document` never appear anywhere in the transcript's written code, which is exactly what the failing tests show (`AssertionError: batch_payload_planner does not export PLAN_FILE_NAME`). This one judgment call is the direct cause of all four g1.r1 fact losses (rule, scope, exclusions_or_crossover, observability) — the agent had, at various points, actually read the exact hash recipe (`l6`, `l7`), two of the four fixture values the grader checks (`say29`, `l7`'s `e3b0c44298fc`), the auto-branch-only scoping (`l14` mail), and the metadata-stays-thin behaviour (`l4`, correctly implemented) — but assembled none of it into the sidecar because it had already filed the whole concept as out of scope.

**The compounding one: a silent wiki bug.** The agent wrote a script that fetches `/api/pages/{id}` for all 114 pages and iterates `d.get("comments", [])`, following the ticket's explicit warning that BookStack search doesn't index comments. It ran this once over all pages (`seq 7 120`) and concluded at line 2477 "No planner mentions in wiki bodies/comments" — but the string `--- COMMENT` never appears anywhere in the transcript's tool output, for any page, meaning the comments field never populated in a single case across the entire corpus. The agent never checked this against a page known to carry a comment, so it never caught the failure. This specifically cost the two wiki-only remarks (`g1.r1.l2`, `g1.r2.l9`), both on `docs/design/batch-job-status-persistence-across-process-restarts.md` — the first of which literally spells out `PLAN_FILE_NAME = "batch_plan.json"`.

A third, smaller miss: message 102 ("Re: Week of Jun 9 recap: bulk inference fix", `g1.r1.l12`, carrying the `BatchLimits`/`dataclasses.asdict`/`max_batches_per_plan` envelope spec) surfaced by subject line in an early IMAP "payload" search but was never opened with the mail-reading script.
