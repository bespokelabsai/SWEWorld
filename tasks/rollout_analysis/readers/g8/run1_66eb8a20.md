## What it missed, and why

**g8.r1.rule (0):** a real implementation bug, not a missing remark. The agent read and correctly
recorded (chat lines 3709, 4345-4346) that `AttachmentTooLarge` fires "inside
`_canonical_attachment_block`, ahead of `file_upload_limit_check`" — but when it wrote the code
(verified from the raw rollout JSON, the `patch_base.py` heredoc), it never actually called
`self.file_upload_limit_check` from inside `_canonical_attachment_block`. Instead the hook call was
placed in a separate loop inside `_handle_multi_modal_prompt`, run only after every block in a
multi-attachment prompt has been built. The grader's `block_of()` test helper calls
`_canonical_attachment_block` directly (bypassing `_handle_multi_modal_prompt` entirely), so a
document-kind block sized at exactly the 24.0 MB ceiling — legally under it, meant to be handed to
the provider hook which then refuses it — sails through untouched, because the hook is simply never
reachable from that code path. This is an **implementation_slip**: the agent's own words match the
requirement, the shipped code doesn't. Its own 25-test unit suite never caught this because none of
its tests exercised the single-block path with a document exactly at the ceiling and a
refusing hook — all of its own test failures during development were setup bugs (abstract methods,
pydantic `validate_default`), never a ceiling-boundary case.

**g8.r2.failure_behavior (0):** a genuine research gap. `normalize_detail` was implemented with the
exact fallback/vocabulary logic required (strip, lowercase, match `_SUPPORTED_IMAGE_DETAILS`,
