## What this run found

The agent's search was thorough and well-sequenced: it read every ticket-referenced source file first, then swept Gitea (736 issues+PRs dumped, nothing attachment-specific), the BookStack wiki (searched by keyword, then — after discovering search doesn't index comments — dumped all 111 pages plus comments whole, still nothing), and IMAP mail (dead end, release-recap boilerplate only). It then correctly identified Mattermost as the real source, authenticated, ran a multi-term keyword search, and pulled the **full** 10,299-post chronological history into a local file it could `grep`/`sed` against for the rest of the run. This let it recover the great majority of the plant: per-kind size ceilings and their exact message wording (`AttachmentTooLarge(kind, size_mb, limit_mb)`, 20.0 image / 24.0 document), the count guard (`_ATTACHMENT_COUNT_LIMIT=12`, `TooManyAttachments`), the fingerprint helper (`sha256:` + 12 hex, empty payload not special-cased, url-vs-base64 hashing rule), the filename cap (`_MAX_ATTACHMENT_FILENAME_LEN=64`, suffix preserved), and the document token cost (`_OPENAI_TOKENS_PER_DOCUMENT=1400`). It also correctly resisted all four herrings: for two of them it never read the *original* herring message (the Jan 21 and Jan 31 threads were never queried), but it read the later reversal threads in full, which fully restate what changed — so the shipped code matches the settled state in every case.

## What it missed, and why

**`g8.r1.scope` — the 45MB whole-prompt ceiling never got built.** The agent read three of the four clues gesturing at this subconclusion — s2-gideon ("that total lives only in `_handle_multi_modal_prompt`"), s2-dario (partially), and petar's "nine legal photos in one cell and the request is still too big" — and even wrote its own reasoning about it at transcript line 4765: *"Count guard: check sits in `_handle_multi_modal_prompt` (where the total already is), raising TooManyAttachments before serializing."* But it channeled all of that reasoning into the attachment-**count** check (which the ticket text already half-implies via `TooManyAttachments`), and never noticed a second, distinct requirement: a **size-sum** check over the base64 blocks with its own 45.0 MB ceiling. The one remark carrying the literal number — s2-nils, "the ceiling wants to be over those... 45 MB is about where they stopped accepting us" — was only half-read: the transcript shows nils's first line (line 2154) but never his second, where the number appears. A search of the full rollout JSON for `45.0`, `_PROMPT`, `whole-prompt`, or `prompt_size` returns zero hits anywhere in the run — confirming no whole-prompt size check was ever written, not even with a wrong number.

**`g8.r2.failure_behavior` — `_SUPPORTED_IMAGE_DETAILS` is missing `"auto"`.** The mechanics of `normalize_detail` are all correct — strip+lowercase, one warning per fallback, none on a hit or on `None`, `Image.detail` left untouched — all pulled from full reads of both reversal threads (rev1, rev2) and l16. But the agent built the vocabulary tuple as `("low", "high")` only, stating explicitly in its own analysis (line 4460): *"`_SUPPORTED_IMAGE_DETAILS` = (\"low\", \"high\") cheapest-first, auto is fallback not a member."* This is the one remark, `g8.r2.l14`, that would have corrected it — "for the module bullet - `_SUPPORTED_IMAGE_DETAILS: tuple[str, ...]`, three entries, and index 0 is what the fallback hands back" — but it never surfaced anywhere in the transcript. The agent instead over-generalized from `fix24`/nikolai's aside ("auto is a diffrent question imo it's not a detail level its a fallback") to conclude auto isn't in the tuple at all, rather than merely not something a caller deliberately sets. It's a near-miss in a real sense: at line 4409, the agent's own plan says *"Need to see the May 13 thread on `_SUPPORTED_IMAGE_DETAILS` membership"* — it was actively hunting for exactly this fact, but searched **forward** from its last clue (Apr 29) to May 13 rather than back to the Apr 24 #viewer thread where l14 actually sits.

## Pattern across both misses

Both losses share the same shape: the agent's search strategy is to stop reading a thread once it has "enough" to move on, and it very rarely re-reads a thread from its start with a wider window once it learns new search terms exist. In both cases the fact-deciding remark was one message away — either the second half of an already-opened thread (s2-nils/45MB), or a thread in a channel/date window it never circled back to despite explicitly looking for exactly that information (l14). Both facts still would have been won with one more targeted `sed -n` read.
